# 變更管理與重新認證指引

本指引處理一個在魚機專案中被系統性低估的問題：**認證的對象不是「這款遊戲」，而是一個特定的建置加上一組特定的數學配置。** 任何偏離該組合的產物，在監管意義上都是未認證的產品，即使它與認證版本只差一行程式碼。

魚機在這一點上比老虎機更脆弱，原因有三：魚種與武器是持續擴充的內容，商業方習慣把它當手遊營運；砲倍檔位與傷害歸屬規則看起來像調參，實際上是數學結構；而傳統機台廠商的開發文化本來就以「現場改機」為常態。

---

## 1. 核心原則

| 原則 | 工程後果 |
|------|----------|
| 認證綁定建置雜湊與配置雜湊 | 產線必須能證明「正在跑的東西」等於「被認證的東西」 |
| 沒有「小修補」這個分類 | 分類由**影響面**決定，不由程式碼行數決定 |
| 數學變更一律產生新的 PAR sheet | 舊 PAR sheet 不能被就地編輯，必須版本化保存 |
| 分類判斷必須留下書面理由 | 事後被質疑時，「我們當時認為不影響數學」需要有依據 |
| 分類存疑時往上歸類 | 低估一次的代價（認證撤銷）遠高於多送一次的成本 |

---

## 2. 變更分類框架

以下五級框架是本 Power 建議的內部工作分類。**它不是任何監管機關的官方分類**（各市場的正式分類與通報門檻標記為 `UNVERIFIED`，須依 `jurisdiction-matrix.md` 的查證 SOP 取得），但它與多數實驗室的實務判斷邏輯一致，可作為內部門檻與送測前自我審查的骨架。

| 類別 | 定義 | 內部驗證 | 送測 | 通報 |
|------|------|----------|------|------|
| 第 0 類 | 純資產替換：美術、音效、動畫，不觸及任何數值或時序 | 資產完整性檢查 + 回歸重播 | 通常不需要，但需記錄 | 依市場，多為不需要 |
| 第 1 類 | UI 佈局、文案、語系、規則說明頁 | UI 回歸 + 規則揭露正確性審查 | 通常不需要；**若修改的是規則揭露文字則需審查** | 記錄 |
| 第 2 類 | 非數學程式修正：崩潰修復、記憶體洩漏、渲染效能，不觸及判定與時序 | 完整回歸 + 重播比對（結果序列須完全相同） | 部分市場要求提交差異說明 | 建議通報 |
| 第 3 類 | 影響數學或判定：賠率、生命值、生成權重、砲倍、傷害歸屬、武器效果 | 完整重新驗證 + 新 PAR sheet | **必須重新送測** | **必須通報** |
| 第 4 類 | 架構或 RNG 變更：RNG 來源、判定架構、伺服器權威模型、獎池控制器 | 完整重新驗證 + RNG 重新提交 | **必須重新送測（範圍最大）** | **必須通報** |

### 2.1 第 2 類的判定門檻：重播必須逐位元相同

第 2 類與第 3 類的界線在實務上最容易誤判。可操作的判準是：

> 以同一組 spawn seed 與同一份事件流重播修改前與修改後的建置，**逐發子彈的判定結果與逐條魚的結局必須完全相同**。若有任何一發不同，該變更就不是第 2 類。

這個判準把「我覺得應該不影響」變成可執行的測試。它也是為什麼 `rng-capture-determination.md` 要求確定性重播能力——重播不只是爭議處理工具，它是變更分類的量測儀器。

### 2.2 時序即數學

渲染優化、物件池調整、tick 頻率變更看起來是第 2 類，但只要它改變了**判定時序**，它就是第 3 類。魚機的判定時序影響的是命中機率：

| 表面上的變更 | 實際影響 |
|--------------|----------|
| 提高伺服器 tick 率 | 碰撞取樣更密，命中率上升 |
| 改變子彈與魚體的碰撞形狀或半徑 | 直接改變命中率 |
| 改變魚的路徑插值方式 | 改變魚的實際可命中面積 |
| 改變射擊請求的排隊或合併方式 | 改變同 tick 內多座位的搶魚結果 |
| 調整回溯（lag compensation）上限 | 改變高延遲座位的期望值 |

最後一項特別容易被當成純網路調參。它改變的是座位間公平性，見 `multiplayer-fairness.md` 第 3 節。

## 3. 魚機變更逐項對照

以下是魚機專案實際會遇到的變更清單，逐項給出分類與理由。這張表是本指引最常被直接使用的部分。

| 變更 | 類別 | 理由與必要動作 |
|------|------|----------------|
| 調整單一魚種的賠率倍數 | 3 | 直接改變 RTP 構成。需重算理論 RTP、重跑模擬、產出新 PAR sheet |
| 調整魚種生命值分佈 | 3 | 生命值決定捕獲成本，等同改變賠率的分母 |
| 新增魚種 | 3 | 新增 RTP 貢獻項，且改變魚群組成比例，使既有魚種的相對出現率變動 |
| 移除魚種 | 3 | 同上，且需確認移除後 RTP 缺口如何補回 |
| 新增或修改特殊武器（雷射砲／冰凍／鎖定追蹤／電磁砲） | 3 | 武器改變每發子彈的期望傷害與覆蓋範圍，是 RTP 的獨立貢獻項 |
| 調整特殊武器的取得條件或充能速度 | 3 | 改變武器的使用頻率，等同改變其 RTP 權重 |
| 修改傷害歸屬或最後一擊規則 | 3（重大） | 改變**座位層期望值**。需完整重新驗證多人情境，且必須同步更新玩家規則揭露 |
| 新增砲倍檔位 | 3 | 必須重新證明各砲倍 RTP 一致性。新檔位常在邊界破壞一致性（例如最高砲倍打小魚時的捨入） |
| 調整既有砲倍的彈值 | 3 | 同上 |
| 調整魚群生成權重 | 3 | 生成權重是 RTP 的主要驅動之一 |
| 修改場景輪替或 BOSS 排程 | 3 | 各場景與 BOSS 關卡有不同 RTP 貢獻，排程即權重 |
| 加入或移除跨桌獎池 | 3（重大） | 獎池重新分配 RTP，是**新的數學配置**，不是一個開關。基礎遊戲 RTP 必須相應調整並重新驗證 |
| 調整獎池抽取比例或必中上限 | 3 | 直接改變獎池與基礎遊戲之間的 RTP 分配 |
| 修改射速上限或自動發射行為 | 3 | 改變單位時間投注量，影響波動性與負責任遊戲評估（見 `responsible-gaming.md`） |
| 修改斷線時已投入傷害的處理規則 | 3 | 改變期望值且改變玩家規則揭露內容 |
| 修改模型 B 的賠付捨入規則 | 3 | 捨入餘數的歸屬影響各座位期望值，雖幅度小但屬數學規則 |
| 修改魚離場條件或場景重置時機 | 3 | 離場與重置是損失項，見 `math-verification.md` |
| 客戶端渲染優化（不觸及判定時序） | 0 或 2 | 純視覺為 0；若涉及邏輯重構則為 2，並須通過重播逐位元比對 |
| 新增語系 | 1 | 但規則說明頁的翻譯正確性須審查，錯譯的規則等同未揭露 |
| 更換魚體美術與音效 | 0 | 前提是碰撞形狀未變 |
| 修改上下分後台選單的權限流程 | 2 或 4 | 若僅 UI 為 2；若改變授權模型則為 4，見 `cabinet-hardware-compliance.md` |
| 更換 RNG 實作或熵源 | 4 | RNG 需重新提交測試 |
| 從客戶端判定改為伺服器權威 | 4 | 這是重寫，不是修改 |
| 更換遊戲伺服器框架或部署拓撲 | 4 | 見 `platform-systems-compliance.md` |
| 修正一個「本身就在影響 RTP」的 bug | 3（特殊） | 見第 6 節，這是最棘手的一類 |

## 4. 台灣：最明確的變更管理法源

台灣的規定是本指引中信心等級最高的部分，因為它是成文且明確的。

| 條文 | 內容 | 信心 |
|------|------|------|
| 第 7 條 | **機具結構或軟體經修改者，視為新型機種，應即依規定申請檢驗及評鑑分類**；且不得陳列、使用未經評鑑分類公告之機台，或擅自修改已評鑑分類之機台 | `HIGH` |
| 第 6 條 | 製造業、進口人或軟體設計廠商應於製造或進口前申請評鑑分類，中央主管機關應於 **30 日內**完成評鑑分類決定並公告；專供出口者不在此限；機具結構另依商品檢驗法申請檢驗 | `HIGH` |
| 第 23 條 | 違反第 7 條第 1 項者，處新臺幣 **10 萬元以上 50 萬元以下**罰鍰 | `HIGH` |
| 第 25 條 | 擅自變更營業級別或機具類別者，處新臺幣 **20 萬元以上 100 萬元以下**罰鍰 | `HIGH` |
| 第 20 條 / 第 34 條 | 主管機關得定期或不定期派員檢查，規避、妨礙或拒絕者處新臺幣 10 萬元以上 50 萬元以下罰鍰 | `HIGH` |

法源：https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=J0080024

### 4.1 工程後果

**台灣沒有「小修補」這個概念。** 第 7 條的文義是「軟體經修改者，視為新型機種」，它不區分修改的性質。這產生三個具體的設計決定：

1. **OTA 更新機制在台灣內銷機台上是高風險設計。** 它讓「擅自修改」在技術上變得容易、在事後變得難以證明未發生。若機台具備 OTA 能力而現場版本與評鑑分類版本不符，舉證責任實務上落在業者身上。若必須保留遠端更新能力，至少應做到：更新需實體授權介入、每次更新寫入不可就地修改的日誌、且更新後的雜湊值可由稽核人員現場讀取。

2. **內銷版與出口版應是不同的建置分支。** 第 6 條的「專供出口者不在此限」使出口版可以有較快的迭代節奏；把兩者混在同一條可 OTA 的產線上，等於把出口版的迭代速度帶進內銷機台的法遵風險。

3. **30 日評鑑分類窗口必須排進專案時程。** 任何第 3 類以上的變更在台灣都意味著至少一個月的行政等待，加上機具結構若同時變動則另有商品檢驗程序。內容更新的排程必須以此為節拍，不能以手遊的雙週更新節奏規劃。

## 5. 建置與認證的綁定

### 5.1 綁定關係

每一份 PAR sheet 必須綁定：

```
parSheetVersion
buildHash          # 遊戲程式二進位的雜湊
configHash         # 數學配置（魚種賠率、生命值分佈、生成權重、砲倍矩陣）的雜湊
rngModuleHash      # RNG 模組獨立雜湊
certificationRef   # 認證報告編號與實驗室
marketCode         # 該配置適用的市場
effectiveFrom / effectiveTo
```

### 5.2 啟動時的強制檢查

**配置雜湊不符即拒絕啟動。** 這是硬要求，不是告警：

| 檢查 | 不符時的行為 |
|------|--------------|
| 建置雜湊不在允許清單中 | 拒絕啟動，記錄事件 |
| 配置雜湊與建置所綁定的值不符 | 拒絕啟動，記錄事件 |
| 配置雜湊有效但無對應的有效認證報告 | 拒絕啟動（這是「配置對了但沒認證」的情況） |
| 市場代碼與部署環境不符 | 拒絕啟動 |
| 運行期定期重驗失敗 | 進入故障狀態並停止接受發射請求，見 `incident-malfunction-handling.md` |

「拒絕啟動」比「記錄並繼續」重要得多，因為後者的實際效果是把未認證建置放進產線並產生真實的玩家交易。實作細節與雜湊驗證時機見 `rng-capture-determination.md`。

### 5.3 可追溯性

從一筆玩家交易，必須能反查到：該桌次當時運行的建置雜湊、配置雜湊、生效的 PAR sheet 版本與認證報告編號。若做不到這件事，事故發生時就無法界定影響範圍，見 `incident-malfunction-handling.md` 第 3 節。

## 6. 已認證建置本身有錯：最棘手的一類

當您發現一個 bug **本身就在影響 RTP**（例如碰撞判定寫錯導致實際 RTP 比 PAR sheet 高 3 個百分點），修這個 bug 不是普通的第 3 類變更，因為它同時揭露了一件事：**已認證的版本從上線起就與其認證文件不符。**

正確的處理順序：

1. **先不要修。** 修復會改變現場行為並讓影響範圍的量測失去基準。先依 `incident-malfunction-handling.md` 的止血與證據保全程序處理。
2. **量測實際偏差與影響期間。** 用歷史重播資料算出實際 RTP 與受影響的交易範圍。
3. **判斷方向。** 實際 RTP **高於**認證值通常是營運商損失、玩家受益；**低於**認證值則是玩家損失，多數市場會要求玩家補償。
4. **同時提交揭露與變更請求。** 只提修復不提揭露，等於隱匿；隱匿在送測紀錄上的後果比原始缺陷嚴重得多，見 `payout-control-integrity.md` 第 6.2 節。
5. **玩家補救方案在提交前先與監管機關對齊。** 補救範圍與方式是否被接受，各市場標記 `UNVERIFIED`。

⚠️ **不要把這類修復偽裝成第 2 類「效能修正」。** 重播逐位元比對會顯示結果序列改變，這件事在實驗室端是可見的。

## 7. 熱修復（Hotfix）

### 7.1 可以熱修復的範圍

| 情況 | 可否熱修 |
|------|----------|
| 崩潰修復，且重播逐位元比對通過 | ✅ 依第 2 類流程，事後補送差異說明 |
| 記憶體洩漏、連線洩漏 | ✅ 同上 |
| UI 顯示錯誤（不含規則揭露內容） | ✅ 第 1 類 |
| 資安漏洞修補（不觸及判定） | ✅ 但需依市場的資安事件通報要求處理 |
| 任何觸及判定、時序、數學、RNG 的修復 | ❌ 不可熱修 |
| 「先上線再補送測」 | ❌ 這是上線未認證建置 |

### 7.2 緊急路徑

當發現的問題屬第 3 或第 4 類、且必須立即停止損害時，**正確的動作是把遊戲下線，不是上線一個未認證的建置**。

停機流程需事先設計：優雅結束進行中的桌次（結算已完成的捕獲、退還未完成捕獲的已投入成本）、對玩家顯示明確原因、記錄停機決定與授權者。魚機的停機比老虎機複雜，因為停機瞬間桌上可能有 8 個座位、多條受傷的魚、進行中的 BOSS 關卡——停機規則必須涵蓋多人同桌情境，見 `multiplayer-fairness.md` 第 6 節。

## 8. 多市場版本策略

### 8.1 每市場配置是獨立的認證產物

常見錯誤是把市場差異做成同一個建置上的功能旗標（feature flag），理由是「維護方便」。這在合規上有兩個問題：

1. 認證的是建置 + 配置的組合。若旗標由執行期環境變數決定，則現場實際生效的組合無法從建置雜湊推知。
2. 旗標讓「用 A 市場的建置跑 B 市場的配置」成為一次部署錯誤即可達成的事，而這件事的後果是在該市場運行未認證產品。

建議做法：**數學配置是版本化的獨立產物，各自有雜湊、各自綁定 PAR sheet 與認證報告**；建置在啟動時驗證「本市場代碼 + 本配置雜湊」是否為已認證組合，不符即拒絕啟動。市場差異矩陣見 `jurisdiction-matrix.md`，配置的數學結構見 `math-model.md`。

### 8.2 共用程式碼的變更擴散

一個判定層的第 3 類變更會擴散到所有市場的配置，意即需要 N 個市場各自重新驗證與重新送測。這是多市場產品的真實成本，必須在變更決策時就估算，而不是在送測時才發現。

| 變更位置 | 擴散範圍 |
|----------|----------|
| 判定引擎、傷害歸屬、RNG | 全部市場 |
| 單一市場的魚種賠率配置 | 僅該市場 |
| 共用魚種資料庫中的某一魚種 | 所有引用該魚種的市場 |

最後一項是實務上最容易漏的：共用的魚種定義庫看起來是資產管理，實際上是跨市場的數學耦合點。

## 9. 法規變動追蹤

變更管理不只涵蓋您改了什麼，也涵蓋**法律改了什麼**。魚機的法律地位在多個市場處於流動狀態，一個專案可能在開發中途失去目標市場。

| 觀察對象 | 為何要追蹤 | 來源 |
|----------|-----------|------|
| 賓州技術遊戲機台訴訟 | 「技術遊戲」的法律地位在州最高法院層級仍在確認中，結論會改變整個 skill-based 定位策略 | https://law.justia.com/cases/pennsylvania/supreme-court/2026/50-map-2024.html |
| 夏威夷 SB3281 | 立法 findings 直接以「fish games」「fish tables」點名，是立法者觀點的第一手證據 | https://data.capitol.hawaii.gov/sessions/session2026/Bills/SB3281_SD1_.HTM |

## 12. 檢查清單

1. 每個建置與配置都有雜湊，且雜湊組合對應到有效的認證報告
2. 配置雜湊不符時系統拒絕啟動，而非記錄後繼續
3. 從任一筆玩家交易可反查當時的建置、配置與 PAR sheet 版本
4. 確定性重播能力已建立，並被用作變更分類的判準
5. 每件變更有書面分類與分類理由
6. 第 3 類以上的變更一律產生新 PAR sheet 並版本化保存舊版
7. 各市場配置為獨立版本化產物，不是同一建置上的執行期旗標
8. 台灣內銷機台的更新路徑已評估 OTA 風險，且 30 日評鑑窗口已排入時程
9. 熱修復範圍已明文定義，緊急情況的路徑是下線而非上線未認證建置
10. 停機流程涵蓋多人同桌的未完成狀態處理
11. 法規觀察清單已建立並有指定負責人
12. 共用魚種／武器定義庫的跨市場耦合已標記

## 需要主動說出的事

1. **認證綁定的是建置雜湊加配置雜湊，不是「這款遊戲」。** 差一行程式碼就是另一個產品。
2. **台灣沒有「小修補」。** 第 7 條規定軟體經修改視為新型機種，須重新申請檢驗及評鑑分類，違反第 7 條第 1 項依第 23 條罰 NT$10 萬–50 萬。這使 OTA 更新機制在內銷機台上是高風險設計。
3. **加入或移除跨桌獎池是新的數學配置，不是一個開關。** 獎池重新分配 RTP，基礎遊戲必須相應重驗。
4. **新增砲倍檔位必須重新證明各砲倍 RTP 一致性。** 新檔位常在邊界的捨入處破壞一致性。
5. **修改傷害歸屬或最後一擊規則會改變座位層期望值**，需完整重新驗證，且必須同步更新玩家規則揭露。
6. **渲染或效能優化若觸及判定時序就不是第 2 類。** 判準是重播逐位元比對，不是主觀判斷。
7. **修一個本身在影響 RTP 的 bug，同時意味著已認證版本一直與認證文件不符。** 必須先保全證據、量測影響、揭露，不能靜默修復。
8. **緊急情況的正確動作是下線，不是上線未認證建置。**
9. **多市場配置做成功能旗標，會讓「現場實際生效的組合」無法從建置雜湊推知**，這在稽核時是難以解釋的架構。
