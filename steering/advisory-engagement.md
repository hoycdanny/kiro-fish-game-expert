# 顧問參與流程指引

本指引定義本 Power 作為魚機合規顧問的標準參與流程：從需求釐清、合規落差評估、風險登記冊、修復路線圖，到交付物與驗收，並劃清機台製造商、遊戲軟體供應商、場所業者與線上營運商之間的責任邊界。

⚠️ **本 Power 提供的是技術合規分析，不是法律意見。** 遊戲的法律分類、牌照義務與刑事風險必須由目標市場的執業律師出具意見。本指引的作用是讓您在找律師之前先把技術事實整理清楚，並在律師給出結論後知道要改哪些程式碼。凡涉及「這樣做會不會違法」的問題，本 Power 的正確輸出是「這是技術事實、這是需要法律確認的爭點、這是查證路徑」，不是結論。

---

## 1. 五階段參與模型

| 階段 | 名稱 | 目的 | 主要產出 |
|------|------|------|----------|
| 1 | 需求釐清與範圍界定 | 確定目標市場、兌現模式與現有架構事實 | 範圍聲明、意向書、必問項答覆記錄 |
| 2 | 合規落差評估 | 逐領域比對現況與目標市場要求 | 落差評估表 |
| 3 | 風險登記冊 | 量化每項落差的機率與衝擊 | 風險登記冊 |
| 4 | 修復路線圖 | 依架構依賴與市場時程排序 | 市場進入路線圖 |
| 5 | 交付物與驗收 | 確認每項修復有可驗證的完成定義 | 驗收清單與送測就緒判定 |

階段順序不可跳。最常見的失敗是跳過階段 1 直接談數學：客戶問「RTP 該設多少」，顧問就開始討論賠率表，六週後才發現目標市場的兌現模式讓整個產品不可能合法部署。

## 2. 階段一：需求釐清與範圍界定

### 2.1 六項基礎變數

這六項對應本 Power 的 onboarding，任何專案在開始技術討論前都必須全部有答案：

| 變數 | 為何決定後續一切 |
|------|------------------|
| 引擎（gameEngine） | 決定 RNG 整合方式與客戶端／伺服器程式碼共用的可行性 |
| 部署形態（deploymentForm） | 決定適用標準是機台類或線上互動系統類，見 `certification-prep.md` |
| 兌現模式（monetisationModel） | 決定法律分類，是六項中最關鍵的一項 |
| 目標市場（targetMarket） | 決定所有數值門檻與是否存在合法部署途徑，見 `jurisdiction-matrix.md` |
| 桌型座位數（tableTopology） | 決定多人公平性驗證範圍與座位間期望值分析情境 |
| 開發階段（developmentStage） | 決定修復是設計選擇還是重寫成本 |

### 2.2 魚機必問項

六項基礎變數不足以評估魚機。以下七項是魚機特有的，且答案通常決定整個專案的可行性。**必須在階段一逐項取得明確答覆，不接受「應該沒有」。**

| 必問項 | 追問方式 | 若答案不利的後果 |
|--------|----------|------------------|
| 是否存在控分機制（控分／場控／保底／記血／回收率調節） | 不要問「有沒有控分」，要問「捕獲判定函式的輸入參數有哪些」 | 架構違規，不是參數問題。見 `payout-control-integrity.md` |
| 判定是否伺服器權威 | 追問「客戶端上報的是什麼，伺服器產生的是什麼」。「客戶端判定、伺服器驗證」不算權威 | 判定層需重寫，見 `platform-systems-compliance.md` |
| 共享魚池模型是 A／B／C | 請對方描述「兩個座位同時打同一條魚，賠付怎麼分」 | 模型 A 需揭露座位間期望值依賴；模型 B 需驗證分配基準。見 `multiplayer-fairness.md` |
| 是否具備對局重播能力 | 追問「能不能用記錄的資料完整重現某一分鐘的桌況」 | 無重播即無變更分類量測儀器，也無爭議處理能力 |
| 各砲倍 RTP 是否一致 | 要求提供逐砲倍的模擬結果，不接受「設計上應該一致」 | 「大砲難打」是退測原因，見 `math-model.md` |
| 是否記錄魚離場 | 追問「被打到剩 5% 血然後游出畫面的魚，資料在哪裡」 | 損失項未揭露，RTP 驗證缺口，見 `math-verification.md` |
| 後台是否有回收率設定項 | 要求匯出完整後台選單樹與每一項的可調範圍 | 未揭露的可調數學參數是退測原因，見 `cabinet-hardware-compliance.md` |

### 2.3 「我們該怎麼開始」的回答順序

這是最常被問到的問題，也是最容易答錯的。**第一個問題永遠是目標市場加兌現模式，永遠不是 RTP。** 正確的決策序列：

1. **目標市場是哪裡？** 若答案是「先做出來再看賣到哪」，就先停下來。魚機的架構約束依市場而異，且部分約束無法事後補上（見第 6.2 節）。
2. **玩家投入什麼、取回什麼？** 現金進現金出、現金進獎品出、現金進不可兌回、虛擬幣不可兌回、sweepstakes——五種模式在同一個市場的法律結論可能完全不同。
3. **在該市場，這個兌現模式下的魚機有沒有合法部署途徑？** 這一題可能的答案包含「沒有」。佛州與北卡是明確的實例：裝置被查扣，不是被罰款。轉 `skill-chance-classification.md` 與 `jurisdiction-matrix.md`。
4. **若有途徑，需要誰的牌照、誰去申請？** 這決定四方責任矩陣的填法（第 3 節）。
5. **適用哪一份技術標準？** 見 `certification-prep.md` 第 2 節的決策樹。
6. **架構是否滿足該標準的不可retrofit項？** 伺服器權威、對局重播、傷害歸屬可稽核性。
7. **然後才談數學。** RTP、波動性、砲倍矩陣。

前六步沒有答案時給出的 RTP 建議是沒有意義的，因為最低派彩率門檻本身就是市場變數。

## 3. 四方責任矩陣

魚機的供應鏈通常有四個角色，而合規義務不會自動落在做決定的那一方。這張矩陣是階段一必須填完的文件。

| 責任項 | 機台製造商 | 遊戲軟體供應商（B2B） | 場所業者 | 線上營運商（B2C） |
|--------|-----------|----------------------|----------|------------------|
| 法律分類風險（是否賭博機具） | 共同：機構設計與硬體形態 | 共同：遊戲機制與呈現 | 主要：實際部署與營業行為 | 主要 |
| 兌現模式合法性 | 硬體是否支援受禁金流裝置 | 賠付上限是否可配置至符合市場 | **主要**：實際兌換行為與獎品價值 | 主要 |
| 型式核准／評鑑分類 | 主要（機具結構） | 主要（軟體） | 次要：僅得陳列已核准機台 | 主要（系統與遊戲） |
| 認證送測執行 | 機台部分 | 遊戲與數學部分 | 無 | 系統與平台部分 |
| RNG 與判定完整性 | 若判定在機台則為主要 | **主要** | 無 | 若判定在其伺服器則為主要 |
| AML／KYC | 無 | 無（提供工具） | 現場現金與獎品環節 | **主要**，見 `aml-kyc-player-account.md` |
| 負責任遊戲功能實作 | 硬體標示與 UI 空間 | 遊戲層功能 | 現場標示與年齡查驗 | **主要**（錢包層限額、自我排除） |
| 資料保護（控制者／處理者） | 通常無 | 通常為處理者 | 控制者（現場會員資料） | **控制者**，見 `data-protection-privacy.md` |
| 變更後重新認證 | 機具結構變更 | **軟體變更**，見 `change-management-recert.md` | 不得擅自修改 | 系統變更 |
| 事故通報 | 協助 | 協助並提供技術根因 | 現場事故 | **主要**，見 `incident-malfunction-handling.md` |

### 3.1 為何要填這張表

未填的後果是可預期的：事故發生時各方都認為對方負責，而監管機關只找持牌那一方。B2B 供應商常以為「我們只賣軟體」就免責，但營運商的牌照條件通常會把技術義務以合約形式下推，且監管機關對供應商本身也可能有註冊要求（例如英國、安大略的 B2B 註冊制度）。**責任邊界應寫進合約，且合約條款必須與這張表一致。**

### 3.2 台灣製造商的「專供出口」陷阱

電子遊戲場業管理條例第 6 條規定製造業、進口人或軟體設計廠商應於製造或進口前就其軟體申請評鑑分類，但**專供出口者不在此限**（信心：`HIGH`，法源 https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=J0080024）。

這條豁免在實務上被理解為：出口機台不需要台灣的評鑑分類，目的地是否合法是買方的事。**就台灣行政法而言，這個理解通常是對的。** 但它在三個層面站不住：

| 層面 | 問題 |
|------|------|
| 商業 | 目的地查扣時買方的損失是整批機台。合約若無明確的合規責任分配與保證條款，爭議會回到製造商 |
| 聲譽 | 佛州 2025 年的執法行動將 fish tables 與違法拉霸機並列查扣（https://flgaming.gov）；北卡 Gift Surplus 判決後場所大規模關閉（https://www.nccourts.gov/documents/appellate-court-opinions/gift-surplus-llc-v-state-ex-rel-cooper）。被公開點名的製造商在受監管市場的後續進入成本顯著上升 |
| 法律（非台灣法） | 目的地市場對「明知供應違法裝置」可能有自己的追訴基礎。此項標記 `UNVERIFIED`，須由目的地市場律師確認 |

顧問應主動指出：**專供出口豁免免除的是台灣的評鑑分類義務，不是目的地的任何義務，也不是商業風險。** 若客戶的出口目的地包含美國各州，第一件事是逐州確認該州對魚機的立場，而非確認台灣的豁免適用性。

## 4. 階段二：合規落差評估

### 4.1 評估領域

落差評估以領域為單位，每個領域對應一份指引。這張對照表也是評估報告的目錄結構。

| 評估領域 | 核心問題 | 對應指引 |
|----------|----------|----------|
| 法律分類 | 在目標市場這是賭博機具、技術遊戲還是違法裝置 | `skill-chance-classification.md` |
| 市場約束 | 獎品上限、年齡、金流裝置、最低派彩率、資料落地 | `jurisdiction-matrix.md` |
| 數學模型 | 魚種賠率、生命值、砲倍矩陣、RTP 構成 | `math-model.md` |
| 數學驗證 | 理論值、模擬值、策略敏感度、PAR sheet | `math-verification.md` |
| RNG 與判定 | CSPRNG、每發獨立性、判定生命週期、稽核欄位 | `rng-capture-determination.md` |
| 派彩控制完整性 | 是否存在補償式控分 | `payout-control-integrity.md` |
| 多人公平性 | 共享模型、傷害歸屬、延遲補償、座位公平 | `multiplayer-fairness.md` |
| 平台與系統 | 伺服器權威、斷線處理、錢包幂等、重播、完整性驗證 | `platform-systems-compliance.md` |
| 機台硬體 | 金流裝置、代幣彩票、後台選單、竄改偵測 | `cabinet-hardware-compliance.md` |
| 認證準備 | 標準適用性、文件集、實驗室 | `certification-prep.md` |
| 負責任遊戲 | 限額、自我排除、自動發射、時間提醒 | `responsible-gaming.md` |
| 變更管理 | 建置與配置綁定、變更分類、通報 | `change-management-recert.md` |
| 事故處理 | 分級、止血、證據保全、補償 | `incident-malfunction-handling.md` |
| AML／KYC | 年齡驗證、帳戶狀態機、同桌價值轉移 | `aml-kyc-player-account.md` |
| 資料保護 | 保存衝突、跨境傳輸、重播資料分類 | `data-protection-privacy.md` |

### 4.2 每項落差的記錄格式

結構化範本：`templates/advisory/compliance-gap-assessment.json`。每項落差至少記錄：

- 領域與具體要求
- 要求來源與信心等級（`HIGH` / `MEDIUM` / `UNVERIFIED`）
- 現況事實（以程式碼、配置或文件為依據，不是客戶口述）
- 落差性質：**架構層 / 數學層 / 流程層 / 文件層**
- 修復是否可retrofit
- 對應的路線圖項目

### 4.3 落差性質分類決定成本量級

| 落差性質 | 典型修復成本 | 例 |
|----------|--------------|-----|
| 文件層 | 低 | PAR sheet 缺少策略區間、缺少損失項揭露 |
| 流程層 | 低至中 | 無變更請求流程、無法規觀察清單 |
| 數學層 | 中 | 各砲倍 RTP 不一致、獎池 RTP 未計入 |
| 架構層 | **高，通常是重寫** | 客戶端判定、無重播、傷害歸屬不可稽核、控分內建於判定路徑 |

顧問在評估報告中必須把架構層落差獨立標示。把它與文件層落差並列成一張清單，會讓客戶低估總成本一個量級。

## 5. 階段三：風險登記冊

### 5.1 評分方式

以機率 × 衝擊評分，範本 `templates/advisory/risk-register.json`。

| 維度 | 分級依據 |
|------|----------|
| 機率 | 該落差在送測或稽核中被發現的可能性。已在後台選單中可見的可調項＝高；深埋於判定路徑的邏輯＝中（但重播比對會揭露） |
| 衝擊 | 退件 < 認證撤銷 < 牌照處分 < 裝置查扣／刑事風險 |

### 5.2 法律地位風險不可用工程手段緩解

⚠️ 風險登記冊必須把**法律地位風險**與**技術合規風險**分欄，因為兩者的緩解路徑完全不同。

| 風險類型 | 緩解者 | 可否用工程降低 |
|----------|--------|----------------|
| 該市場是否存在合法部署途徑 | 律師 + 監管機關 | ❌ 不能。調整技術成分不會改變 any-chance 測試的結論 |
| 兌現模式是否構成賭博 | 律師 | ❌ 不能 |
| 最低派彩率是否達標 | 數學團隊 | ✅ 可 |
| 是否有控分 | 工程團隊 | ✅ 可（移除） |
| 是否伺服器權威 | 工程團隊 | ✅ 可（重寫） |

英國的情形是最清楚的例子：UKGC 對 SWP 的指引明確指出，只要遊戲結果**可以**被機率影響，即為 Gambling Act 2005 意義下的 game of chance，機率成分是否大於技術成分、能否被高超技術消除，均不影響認定（https://www.gamblingcommission.gov.uk/licensees-and-businesses/guide/skill-with-prizes-swps）。**在這個測試下，「提高技術權重」這個工程動作對分類結果的貢獻是零。** 顧問若讓客戶花六個月做技術貢獻度優化來規避英國分類，那是把不可緩解的風險當成可緩解的處理。

法律地位風險的正確處置是升級（第 7 節），不是列入路線圖等工程解決。

## 6. 階段四：修復路線圖

### 6.1 排序輸入

範本 `templates/advisory/market-entry-roadmap.json`。排序需同時考慮：

1. 架構依賴（哪些修復是其他修復的前提）
2. 市場上線時程與認證行政窗口（例如台灣第 6 條的 30 日評鑑分類決定期，信心 `HIGH`）
3. 落差的衝擊等級
4. 團隊能力與可平行度

### 6.2 排序硬規則：架構約束必須在第一版

⚠️ **以下三項無法retrofit，若範圍內有任何嚴格市場，就必須進第一版：**

| 架構約束 | 為何不可retrofit |
|----------|------------------|
| 伺服器權威判定 | 從客戶端判定改為伺服器權威是重寫判定層，不是加一層網路。且既有的客戶端預測、動畫時序、狀態同步全部要重做 |
| 對局重播能力 | 重播要求判定路徑本身是確定性的，且所有輸入（spawn seed、事件流、配置雜湊）被記錄。事後加記錄無法補回過去的可重播性，而重播是變更分類的量測儀器（見 `change-management-recert.md` 第 2.1 節） |
| 傷害歸屬可稽核性 | 若原設計只記錄最後一擊，過去的爭議永遠無法回答；且模型 B 的分配基準若一開始就是傷害量而非投入成本，改基準等同改數學 |

實務建議：即使客戶第一階段只做社交／無兌現版本，只要三年內的路線圖中有任何真錢市場，這三項就應在第一版建立。它們的邊際成本在專案初期是低的，在上線後是重寫。

### 6.3 典型排序骨架

| 順位 | 工作 | 理由 |
|------|------|------|
| 0 | 法律地位確認（律師） | 若無合法途徑，其後皆無意義 |
| 1 | 移除控分、判定層改為伺服器權威、建立確定性重播 | 架構層，其他工作的前提 |
| 2 | 傷害歸屬與損失項（含魚離場）記錄完整化 | 數學驗證的資料前提 |
| 3 | 數學模型重新設計與驗證（含各砲倍一致性、策略區間） | 依賴 1 與 2 |
| 4 | 錢包幂等性、斷線處理、完整性驗證 | 平台層，可與 3 平行 |
| 5 | 負責任遊戲與 AML／KYC 功能 | 錢包層，可與 3、4 平行 |
| 6 | 後台選單可調項盤點與凍結 | 送測文件前提 |
| 7 | 文件集撰寫與實驗室對接 | 依賴全部 |
| 8 | 變更管理流程上線 | 認證後維持有效性的前提 |

## 7. 應停止參與並升級的紅旗

以下情形出現時，顧問的正確動作是停止技術建議、明確說明理由，並要求客戶取得法律意見。**繼續給技術建議會讓客戶誤以為問題只是技術問題。**

| 紅旗 | 為何要停 |
|------|----------|
| 目標市場為已明確查扣同類裝置的司法管轄區，而客戶仍要求「怎麼設計才不會被抓」 | 這是規避執法的諮詢，不是合規諮詢 |
| 要求協助設計控分但「做得看不出來」 | 隱匿本身的後果比原始違規更重，見 `payout-control-integrity.md` 第 6.2 節 |
| 要求把已認證版本以外的建置上線，「先上再補送測」 | 這是在產線上運行未認證產品 |
| 要求繞過年齡驗證或自我排除名單 | 直接牴觸玩家保護義務 |
| 要求以 sweepstakes 或「純娛樂」包裝實質現金兌現 | 分類爭點，必須由律師判斷，且多個市場已有不利判決 |
| 客戶無法或拒絕說明捕獲判定的輸入參數 | 無法評估的系統不能被背書 |
| 客戶要求本 Power 出具「合規」結論以對外使用 | 本 Power 提供技術分析，不出具合規證明 |

升級的形式應是書面：記錄爭點、記錄客戶的要求、記錄已告知的風險，並註明需要法律意見的具體問題。

## 8. 階段五：交付物與驗收

### 8.1 交付物

| 交付物 | 範本 | 驗收標準 |
|--------|------|----------|
| 範圍聲明與必問項答覆記錄 | — | 六項基礎變數與七項魚機必問項全部有明確答覆，無「應該沒有」 |
| 合規落差評估表 | `templates/advisory/compliance-gap-assessment.json` | 每項落差有來源、信心等級、落差性質與可retrofit判定 |
| 風險登記冊 | `templates/advisory/risk-register.json` | 法律地位風險與技術風險分欄；每項有負責人與複查頻率 |
| 市場進入路線圖 | `templates/advisory/market-entry-roadmap.json` | 架構層項目位於第一版；行政窗口已計入時程 |
| 四方責任矩陣 | — | 每一格有指定角色，無空格；與合約條款一致 |
| 法規觀察清單 | — | 有來源 URL、負責人、複查頻率 |
| 事故報告範本落地 | `templates/advisory/incident-report.json` | 已納入營運流程，非僅存檔 |

### 8.2 驗收原則

每項修復的完成定義必須是**可驗證的產物**，不是「已完成」的口頭確認：

| 修復類型 | 可驗證的完成定義 |
|----------|------------------|
| 移除控分 | 通過 `payout-control-integrity.md` 第 3.3 節的三項行為測試，並保留測試輸出 |
| 伺服器權威 | 客戶端無捕獲判定程式碼路徑；伺服器判定日誌完整 |
| 對局重播 | 同一 spawn seed 與事件流重播結果逐位元相同 |
| 各砲倍 RTP 一致 | 逐砲倍模擬結果落在統計誤差內，附樣本量推導 |
| 損失項記錄 | 魚離場與場景重置事件可查詢，且已納入 RTP 驗算 |
| 後台可調項盤點 | 完整選單樹匯出，每項有可調範圍與對應 PAR sheet |

### 8.3 送測就緒判定

顧問不宣告「合規」，只宣告「送測就緒」或「未就緒並列出阻礙項」。就緒的最低條件見 `certification-prep.md` 的送測就緒檢查清單。**任何架構層落差未關閉，即為未就緒，不論文件多完整。**

## 需要主動說出的事

1. **第一個問題永遠是目標市場加兌現模式，不是 RTP。** 在市場與兌現模式未定之前討論的所有數值都可能作廢。
2. **「先做出來再看賣到哪」對魚機不成立。** 伺服器權威、對局重播、傷害歸屬可稽核性三項無法retrofit，缺一項就是重寫。
3. **台灣的專供出口豁免只免除台灣的評鑑分類義務**，不免除目的地的任何義務，也不免除商業與聲譽風險。目的地包含佛州或北卡時，裝置的結局是被查扣。
4. **四方責任矩陣沒填完，事故時就會出現各方互指。** 監管機關只找持牌那一方，而牌照條件通常把技術義務以合約下推到供應商。
5. **法律地位風險不能用工程緩解。** 在英國 any-chance 測試下，提高技術權重對分類結果的貢獻是零；花六個月做技術貢獻度優化來規避英國分類是浪費。
6. **架構層落差與文件層落差不能列在同一張清單上**，那會讓客戶低估總成本一個量級。
7. **「有沒有控分」不能直接問。** 要問捕獲判定函式的輸入參數有哪些，並要求匯出完整後台選單樹。
8. **本 Power 不出具合規結論，只出具送測就緒判定。** 客戶要求對外可用的合規證明時，正確回應是轉介實驗室與律師。
9. **紅旗出現時要書面升級。** 繼續提供技術建議會讓客戶誤以為問題只是技術問題。
