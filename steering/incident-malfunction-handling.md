# 事故與故障處理指引

本指引涵蓋魚機事故的分級、止血與證據保全順序、多人同桌事故的特殊處理、玩家補救判定、監管通報，以及事後的預防性設計。

魚機的事故處理與老虎機有一個結構性差異，這個差異決定了本指引的整體形狀：**老虎機的事故通常只影響一名玩家，魚機的事故幾乎一定影響整桌。** 一次傷害歸屬錯判會同時造成一個座位多得、另一個座位少得；一次桌次崩潰會讓 8 個座位同時處於未完成狀態。因此魚機的補救不是「賠給申訴的人」，而是**重建整張桌在整個時間窗內的正確結果**。

---

## 1. 處理順序：止血 → 保全 → 界定 → 修復

⚠️ **最常見的錯誤是先修再查。** 修復會覆寫記憶體狀態、輪替日誌、觸發配置重載，而這些正是界定影響範圍所需的證據。一旦證據消失，您就無法回答「哪些座位該被補多少」，補救就退化為對申訴者的個案安撫，而這在監管檢視下是不可接受的。

| 階段 | 目標 | 不可做的事 |
|------|------|-----------|
| 1. 止血 | 停止損害擴大 | 不要「順手」修程式 |
| 2. 保全 | 凍結證據 | 不要重啟服務、不要清理日誌、不要重載配置 |
| 3. 界定 | 算出受影響的座位、玩家、交易與時間窗 | 不要只看申訴者的紀錄 |
| 4. 修復 | 依 `change-management-recert.md` 的分類走變更流程 | 不要熱修第 3、4 類變更 |
| 5. 補救與通報 | 執行玩家補救、依市場要求通報 | 不要在未確認政策前追扣玩家 |
| 6. 預防 | 加入不變式檢查與回歸案例 | 不要只留一份事故報告就結案 |

### 1.1 止血的可用手段

| 手段 | 適用 | 副作用 |
|------|------|--------|
| 停止該桌開新局 | 局部缺陷 | 低 |
| 關閉特定砲倍或特定魚種 | 缺陷可定位到配置項 | 中，改變 RTP，須記錄為臨時偏離 |
| 關閉整個遊戲 | 數學或判定缺陷 | 高，但通常是正解 |
| 關閉跨桌獎池 | 獎池控制器缺陷 | 需處理已累積金額的歸屬 |
| 凍結出款 | 疑似舞弊或價值轉移 | 需依 `aml-kyc-player-account.md` 的帳戶處置流程，不可任意為之 |

**關閉特定砲倍或魚種會使實際生效配置與認證配置不符。** 這是刻意的臨時偏離，必須記錄、限期、並納入事後通報，不能變成常態。

## 2. 嚴重度分級

| 等級 | 定義 | 魚機範例 | 目標反應 |
|------|------|----------|----------|
| P1 | 影響遊戲公正性、玩家資金正確性，或涉及未授權建置／配置上線 | 實際 RTP 偏離認證值、傷害歸屬系統性錯判、跨桌獎池雙重派出、未經授權配置上線、自我排除玩家仍能發射 | 立即止血，立即啟動保全 |
| P2 | 影響部分玩家的結果或餘額，但無系統性公正性問題 | 單一桌次崩潰、單筆上下分錯誤、模型 B 捨入錯誤、場景重置導致已投入傷害歸零 | 當日止血與界定 |
| P3 | 影響體驗與可稽核性，未直接影響金額 | 魚群狀態不同步、重播事件流缺漏、搶魚未正確呈現 | 排入修復，但可稽核性缺漏須即時補上 |
| P4 | 表現層缺陷 | 美術錯誤、音效缺失、文案錯字 | 常規排程 |

### 2.1 兩個必須直接升為 P1 的類別

**未經授權的配置或建置上線。** 即使它「看起來沒造成損害」，它本身就是在受監管市場運行未認證產品。影響範圍是該建置運行期間的**全部**交易，不是有人抱怨的那幾筆。

**自我排除玩家仍能發射，或未成年玩家入場。** 這類事故的嚴重性不在金額而在許可條件本身。金額可以補救，違反玩家保護義務不能用退款抵銷。發射請求的帳戶狀態檢查應在捕獲生命週期的第一階段就攔截（見 `aml-kyc-player-account.md` 第 2 節與 `responsible-gaming.md`）；若這個攔截失效，代表閘門位置設計錯誤，不只是一個 bug。

## 3. 證據保全：魚機需要保全的比錢包帳本多得多

### 3.1 為什麼錢包帳本不夠

事故發生後真正要回答的問題是「**這條魚的賠付本來應該歸誰、歸多少**」。錢包帳本只記錄實際發生的餘額變動，它無法告出應然結果。要重建應然結果，必須有該桌在該時間窗的完整對局重播材料。

### 3.2 保全清單

發現 P1 或 P2 事故後，立即對受影響的桌次與時間窗（**時間窗要往前後各留足夠餘裕**，因為事故的起始點通常比察覺點早）快照下列材料：

| 材料 | 為何需要 |
|------|----------|
| 對局重播事件流（逐發子彈、逐次傷害、逐條魚結局） | 重建應然結果的唯一依據 |
| 魚群 spawn seed 與生成參數 | 沒有 seed 就無法確定性重播 |
| 逐條魚的完整傷害序列與 `killingBulletId` | 判定歸屬正確性 |
| 各座位的進出場時間與砲倍切換歷程 | 界定受影響玩家名單，含已離桌者 |
| 錢包帳本與交易 ID | 比對應然與實然的差額 |
| 當時生效的建置雜湊、配置雜湊、PAR sheet 版本 | 判斷是配置問題或程式問題 |
| 伺服器 tick 日誌與回溯量記錄 | 時序類缺陷的唯一線索 |
| 跨桌獎池的累積與派出事件 | 獎池類事故 |
| 錯誤日誌、崩潰轉存、部署歷史 | 根因分析 |

### 3.3 保全的實作要求

- 快照必須是**唯讀複本**，不可在原始儲存上「就地保留」，因為輪替與壓縮政策會照常執行。
- 快照必須包含足以離線重播的完整輸入，而不只是可讀的摘要。
- 快照必須記錄執行者、時間與涵蓋範圍，本身可稽核。
- ⚠️ 快照包含其他玩家的個人資料。保全與存取需依 `data-protection-privacy.md` 的存取控制與最小化要求處理；「為了查事故」不是無限存取個資的授權。

重播能力的資料欄位設計見 `rng-capture-determination.md`；重播基礎設施見 `platform-systems-compliance.md`。

## 4. 魚機事故目錄

| 事故 | 魚機特有的處理要點 |
|------|-------------------|
| 實際 RTP 偏離目標 | 用歷史重播算出實際值與偏差方向。偏低通常需玩家補救，偏高是營運商損失但仍是認證不符。同時檢查是否為隱藏的補償控制器所致（見 `payout-control-integrity.md`） |
| 傷害歸屬錯判 | **雙向補救**：一個座位多得、另一個少得。不能只補少得方而不處理多得方，否則帳務無法平衡 |
| 最後一擊判定錯誤 | 需重播確認 `killingBulletId`。模型 A 下全額賠付的歸屬錯誤金額大，優先處理 |
| 模型 B 賠付分配捨入錯誤 | 影響**該魚全部貢獻座位**，包含事故發現時已離桌的玩家。必須從傷害序列反查全部參與者，不能只處理仍在線者 |
| 上下分錯誤 | 需與硬體計數器、軟體計數器三方對帳（見 `cabinet-hardware-compliance.md`）；線上則需錢包雙式記帳對帳 |
| 桌次崩潰且多座位進行中 | 全桌一致處理：結算已完成捕獲、退還未完成捕獲的已投入成本。**不可只補償申訴者** |
| 單一座位斷線時已投入傷害的處理 | 若事前無明文規則，這不是事故而是設計缺口。規則必須事先定義並揭露（見 `multiplayer-fairness.md` 第 6 節） |
| 場景重置導致已投入傷害歸零 | 若這是設計預期行為且已揭露，屬損失項而非事故；若未揭露，則是揭露缺失事故 |
| 跨桌獎池雙重派出或漏派 | 雙重派出涉及追扣（見第 5.3 節）；漏派需回溯全部參與桌次的玩家名單 |
| 魚群狀態不同步 | 判定權威狀態，全桌重新同步。若各客戶端顯示不同魚況，需確認是否已有玩家依錯誤畫面下注 |
| 未經授權的配置或建置上線 | P1。影響範圍是該建置的全部運行期間 |
| 自我排除玩家仍能發射 | P1。金額退還之外，須檢視閘門位置與名單同步機制 |
| 未成年玩家入場 | P1。實體場所另涉台灣第 17 條第 1 項第 1、2 款的入場限制 |
| 特殊武器效果異常 | 雷射貫穿或鎖定追蹤的判定異常會使該武器期間的 RTP 偏離，需以武器使用事件界定範圍 |
| 魚離場率異常 | 通常指示碰撞或彈道實作缺陷。離場魚的紀錄是唯一線索，這也是為何離場魚必須記錄 |

## 5. 多座位補救問題

這是魚機事故處理最困難的部分，也是最需要在事故發生前就有政策的部分。

### 5.1 為何不能只補救申訴者

假設座位 3 申訴「我打掉金龍 90% 的血，賠付卻給了座位 5」。若重播證實判定錯誤，那麼：

- 座位 3 應得而未得。
- **座位 5 已得而不應得。**
- 同桌其他座位在模型 B 下也各有應得份額變動。
- 這條魚之後的魚群狀態、玩家餘額、後續下注決策都建立在錯誤結果之上。

只補座位 3，帳務上等於營運商自行吸收座位 5 的多得。金額小時這是合理的商業決定；但若缺陷是系統性的、跨越數千桌次，吸收總額可能無法承受，而且**只補申訴者意味著沒申訴的受害座位未被補救**，這在監管檢視下是選擇性補救。

### 5.2 界定範圍的正確作法

1. 以缺陷的**技術特徵**界定範圍，不以申訴界定。例如「所有在版本 X 期間、同 tick 內有兩發以上子彈命中同一條魚的桌次」。
2. 對範圍內全部桌次重播，比對應然與實然。
3. 產出逐玩家的差額清單，含已離桌與已停用帳戶。
4. 分別統計「應補」與「多得」總額。
5. 依政策決定多得部分的處理。

### 5.3 追扣（clawback）：預設不做

從玩家帳戶追回多得金額在多數市場是敏感行為，其可行性依市場、依營運商條款、依金額而定。

**本 Power 的立場：追扣的可接受性逐市場標記 `UNVERIFIED`**，須在事故發生前就取得書面依據（營運商條款 + 監管機關立場），不可在事故當下臨時決定。

| 情況 | 建議 |
|------|------|
| 無明文條款與監管立場 | 不追扣，營運商吸收 |
| 有條款且金額小 | 通常吸收成本低於爭議成本 |
| 有條款且金額大、或涉及舞弊 | 依條款處理，並先與監管機關溝通 |
| 疑似共謀取得 | 走帳戶處置流程，見 `aml-kyc-player-account.md`，不是一般追扣 |

⚠️ **在沒有明文政策與監管立場的情況下從玩家帳戶扣款，本身可能成為第二起事故。**

## 6. 「malfunction voids pays」條款

幾乎所有機台與線上遊戲條款都有「故障時所有賠付與投注無效」的文字。關於它的實際效力，有兩件事必須說清楚：

1. **它可以處理偶發的技術故障**（例如通訊中斷造成的顯示錯誤、單次結算未完成），這是它的設計用途。
2. **它不能免除系統性設計缺陷的責任。** 若實際 RTP 因為實作錯誤而長期偏離認證值，那不是「故障」而是產品與其認證文件不符。以 voids pays 條款主張全部相關賠付無效，實質上是要求玩家承擔供應商的設計錯誤。

各市場對此條款在設計缺陷情境下的接受度標記 `UNVERIFIED`，須逐市場確認。但在諮詢對話中應直接說明：**不要把這個條款當成 RTP 缺陷的免責方案來規劃**，因為它在多數受監管市場不會被接受，且主張它本身會被解讀為迴避責任。

實務建議：條款文字應區分「單次交易層級的技術故障」與「產品層級的缺陷」，後者明示將依監管要求處理並提供玩家補救。這比一個涵蓋一切的免責條款更站得住腳。

## 7. 監管通報

### 7.1 通報門檻與時限

⚠️ 魚機事故的通報門檻與時限**逐市場而定，且多數市場沒有針對魚機的專門規定**，整體標記 `UNVERIFIED`。取得途徑：

| 來源 | 可查到什麼 |
|------|-----------|
| 丹麥 Spillemyndigheden 認證方案（SCP.00–SCP.07） | 模組化的控制項要求，可作為內部事件管理與資安通報的檢查骨架：https://spillemyndigheden.dk/en-us/businesses-and-associations/games-which-require-a-licence/online-casino/certification-programme-for-online-casino |
| AGCO Registrar's Standards for Internet Gaming | 線上遊戲的紀錄保存與營運要求，須逐條檢核：https://www.agco.ca/en/lottery-and-gaming/guides/registrars-standards-internet-gaming |
| 台灣主管機關檢查權 | 條例第 20 條規定主管機關得定期或不定期派員檢查，不得規避、妨礙或拒絕；第 34 條罰則 NT$10 萬–50 萬（`HIGH`）：https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=J0080024 |
| 營運商的牌照條件與實驗室認證報告條件 | 通常直接寫明通報義務，這是最快的來源 |

### 7.2 唯一有明確時限的類別

**個人資料外洩：GDPR 第 33 條要求在知悉後 72 小時內通報主管機關**，第 34 條規範對資料主體的通知（`HIGH`）。這與遊戲公正性事故是不同的通報軌道，觸發條件也不同——一次傷害歸屬錯判不是個資外洩，但一次重播資料庫外流是。兩條軌道可能同時觸發，處理流程見 `data-protection-privacy.md`。

### 7.3 B2B 供應商的通報位置

遊戲供應商通常不直接持有向監管機關通報的義務（該義務多在營運商），但供應商有**及時告知營運商**的合約義務，且延遲告知會直接造成營運商違反其通報時限。責任邊界應在合約中明定，見 `advisory-engagement.md`。

## 8. 事故報告

每件 P1、P2 事故應產出結構化報告：時間軸、嚴重度、根因、受影響範圍（桌次／座位／玩家／交易／金額）、應然與實然差額、止血措施、保全範圍、補救方案與執行狀況、通報對象與時間、預防措施與回歸案例編號、以及變更請求編號。

範本：`templates/advisory/incident-report.json`。若事故導致需要修復，該修復依 `change-management-recert.md` 分類走變更流程，並使用 `templates/certification/change-management-request.json`。事故若揭露了系統性風險，應同步更新 `templates/advisory/risk-register.json`。

## 9. 預防性設計：把事故變成不變式

事故處理的最終產出不是報告，而是讓同類事故無法靜默發生的檢查。以下是魚機值得實作的不變式與監控。

### 9.1 執行期不變式

| 不變式 | 違反時的行為 |
|--------|--------------|
| 逐座位賠付總和 == 該魚應付總額 | 拒絕結算該魚，記錄 P1 事件並凍結該桌 |
| 逐條魚的傷害總和 <= 初始生命值 | 記錄異常，重播該魚 |
| 每發子彈恰有一筆扣款與一筆判定紀錄 | 錢包與判定不一致即告警 |
| 錢包雙式記帳借貸平衡 | 拒絕交易 |
| 跨桌獎池：累積 - 派出 == 當前餘額 | 凍結獎池 |
| 每筆派出的獎池事件 ID 唯一（幂等） | 拒絕重複派出 |
| 建置與配置雜湊符合已認證組合 | 拒絕啟動或進入故障狀態 |
| 發射請求者的帳戶狀態為「有效」 | 拒絕發射 |

**逐座位賠付總和等於應付總額**是模型 B 最重要的不變式，因為捨入錯誤在單筆上極小、在總量上可觀，且不會有玩家察覺後申訴——它只會被對帳或事後審查發現。

### 9.2 統計監控

| 監控 | 告警條件 |
|------|----------|
| 逐桌與全域 RTP 滑動窗口 | 偏離認證值超出統計預期區間 |
| 逐砲倍 RTP | 各砲倍之間出現系統性差異（違反一致性要求） |
| 逐座位 RTP 與命中率 | 特定座位長期偏離（座位公平性缺陷） |
| 魚離場率 | 偏離模型預期（碰撞或彈道缺陷） |
| 最後一擊分佈 | 特定座位或帳號對異常集中（缺陷或共謀，後者見 `aml-kyc-player-account.md`） |
| 重播完整性抽樣 | 隨機抽樣重播並比對實際結算結果 |

最後一項是最有價值也最少被實作的：**定期隨機抽樣重播並比對實際結果**，是唯一能主動發現「靜默偏差」的機制。它同時是送測時極有說服力的自我驗證材料。

### 9.3 回歸案例

每件 P1、P2 事故都應轉為一個**基於重播的自動回歸案例**：保存事故當時的 spawn seed 與事件流，作為固定測試輸入，並斷言修復後的建置產生正確結果。這批案例同時是 `change-management-recert.md` 第 2.1 節逐位元比對的測試資產。

---

## 需要主動說出的事

1. **先修再查會摧毀界定影響範圍所需的證據。** 順序是止血 → 保全 → 界定 → 修復，不可調換。
2. **魚機的證據保全必須包含對局重播事件流與 spawn seed，不只是錢包帳本。** 錢包只記錄發生了什麼，重播才能算出應該發生什麼。
3. **傷害歸屬錯判是雙向的**：一方多得、一方少得，且模型 B 的捨入錯誤會波及已離桌玩家。只補少得方會使帳務無法平衡，也構成選擇性補救；必須從傷害序列反查全部參與者。
4. **補救範圍必須以缺陷的技術特徵界定，不以玩家申訴界定。** 沒申訴的受害座位同樣要被補。
5. **在沒有明文條款與監管立場前不要從玩家帳戶追扣。** 追扣的可接受性逐市場 `UNVERIFIED`。
6. **「malfunction voids pays」不能用來免除系統性 RTP 缺陷的責任**，不要把它當成缺陷的免責規劃。
7. **未授權建置或配置上線一律是 P1**，影響範圍是該建置的全部運行期間，不是被抱怨的那幾筆。
8. **GDPR 第 33 條的 72 小時通報只適用於個人資料外洩**，與遊戲公正性事故是不同軌道；後者的通報門檻多為 `UNVERIFIED`，須查牌照條件。
9. **定期隨機抽樣重播並比對實際結算，是唯一能主動發現靜默偏差的機制**，也是送測時最有力的自我驗證材料。
