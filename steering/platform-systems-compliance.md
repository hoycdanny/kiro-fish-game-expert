# 平台與系統層合規指引

本指引涵蓋線上魚機的系統層要求：持續權威世界的伺服器架構、tick 時序、斷線與未完成局處理、上下分與錢包幂等性、對局重播、軟體完整性驗證、跨桌獎池控制器、監管機關中央系統整合、稽核日誌基礎設施與容量、以及資料落地對部署拓撲的影響。

魚機的系統層與老虎機的系統層不是同一種東西。老虎機的遠端遊戲伺服器（RGS）本質上是無狀態的：收到一次 spin 請求、產生結果、回傳、結束。魚機的伺服器必須維持一個**持續運行的權威世界**——魚群的位置、速度、剩餘生命值、道具狀態、以及 4 到 10 個座位同時進行的射擊——而這個世界的每一個 tick 都在產生具有金錢後果的判定。

---

## 1. 適用標準範圍

依亞利桑那州部落協議 Appendix A 的官方設備對標準對照（https://gaming.az.gov/sites/default/files/Appendix%20A%20-%20Generic_1.pdf，信心 `HIGH` 就該文件本身而言）：

| 設備類型 | 對應標準 | 魚機專案何時適用 |
|----------|----------|------------------|
| Gaming Devices | GLI-11 | 實體機台部署 |
| Progressive Gaming Devices | GLI-12 | 有跨桌獎池 |
| Online Monitoring Systems | GLI-13 | 有中央監控／稽核系統 |
| Bonus Systems | GLI-17 | 獨立的紅利系統 |
| Promotional Systems | GLI-18 | 促銷／回饋系統 |
| Redemption Kiosks | GLI-20 | 彩票或獎品兌換機 |

線上互動系統另適用 GLI-19。**一個典型的線上魚機專案不是「送 GLI-11」，而是 GLI-19 加 GLI-12 加可能的 GLI-13。** 混合部署（機台 + 線上）則兩軌並行。標準索引：https://gaminglabs.com/gli-standards/，適用性決策樹見 `certification-prep.md` 第 2 節。

丹麥 Spillemyndigheden 的認證方案把**基礎平台獨立列為 SCP.02**，與 SCP.01（RNG）、SCP.03（ISMS）、SCP.04（滲透測試）、SCP.05（弱點掃描）、SCP.06（變更管理）、SCP.07（遊戲要求）並列（https://spillemyndigheden.dk/en-us/businesses-and-associations/games-which-require-a-licence/online-casino/certification-programme-for-online-casino）。即使目標市場不是丹麥，SCP.02 的模組邊界是一份可直接借用的平台層檢查清單骨架：平台的完整性、可用性、記錄與存取控制是**與遊戲數學分開被審查的**。

## 2. 伺服器架構：每桌一個 tick loop

### 2.1 與老虎機 RGS 的結構差異

| 面向 | 老虎機 RGS | 魚機遊戲伺服器 |
|------|-----------|----------------|
| 狀態 | 無狀態（狀態在錢包與交易紀錄） | 每桌持續的權威世界狀態 |
| 觸發 | 客戶端請求驅動 | 伺服器 tick 驅動 + 客戶端事件注入 |
| 一次判定的粒度 | 一次 spin | 一發子彈；一次捕獲可能跨數十發、數秒 |
| 並發 | 請求彼此獨立 | 同桌座位彼此耦合（共享魚池） |
| 崩潰後果 | 單一未完成 spin | 整桌多座位的未完成狀態 + 魚群狀態遺失 |
| 水平擴展 | 任意分散 | 桌是不可分割的親和單位（table affinity） |

**桌是不可分割的親和單位。** 同一桌的所有判定必須在同一個權威實例上執行，否則共享魚池的生命值扣減會出現競態。這使部署拓撲不能採用「請求隨機分派到任一節點」的無狀態模型，必須有明確的桌到節點的映射，以及節點失效時的桌次遷移或收攤規則。

### 2.2 tick 頻率是認證參數，不是效能調校項

⚠️ **伺服器 tick 頻率與判定時序是已認證的數學參數。** 提高 tick 率會讓碰撞取樣更密、命中率上升；改變射擊請求的排隊或合併方式會改變同 tick 內多座位的搶魚結果。這些是第 3 類變更，需重新驗證與送測，見 `change-management-recert.md` 第 2.2 節「時序即數學」。

工程後果：

- tick 頻率必須是**配置值並納入 configHash**，不是編譯期常數或依機器負載自適應的變數。
- 不得在高負載時降低 tick 率以維持穩定。負載保護的正確做法是限制每節點的桌數，或拒絕開新桌。
- tick 執行超時（一個 tick 的處理未在下一個 tick 前完成）必須記錄為事件並告警，因為它代表判定時序已偏離認證值。
- 客戶端渲染 tick 與伺服器判定 tick 必須是分離的概念。客戶端可以 60 fps 渲染，判定仍以伺服器 tick 為準。

### 2.3 伺服器權威結果決定

判定必須由伺服器產生，且判定所需的隨機位元由伺服器端 CSPRNG 取得。實作細節見 `rng-capture-determination.md`。

「客戶端判定、伺服器驗證」不構成伺服器權威：若伺服器僅檢查客戶端上報的結果是否落在合理範圍，攻擊者可在合理範圍內持續選擇對自己最有利的結果。見 `multiplayer-fairness.md` 第 3.4 節。

判定路徑的最小輸入集：魚的當前權威狀態、砲倍、伺服器 CSPRNG 位元、已驗證雜湊的配置。**不包含**客戶端提交的時間戳、客戶端聲稱的命中結果、玩家累積統計。

## 3. 斷線與未完成局處理

老虎機的未完成局定義清楚：一次 spin 已扣款但結果未交付。魚機沒有這麼乾淨的邊界，因為「一次遊戲」的原子單位是**一發子彈**，而玩家關心的結果單位是一次捕獲，兩者的時間跨度不同。

### 3.1 必須事先定義並揭露的四種情境

| 情境 | 需定義的規則 | 常見選項 |
|------|--------------|----------|
| 座位斷線，該座位在活魚身上有累積傷害 | 傷害是否保留、其他座位可否撿現成、重連後可否延續 | (a) 傷害保留於魚身，其他座位可完成擊殺（模型 A 下等於把投入送給別人）；(b) 依模型 B 的投入成本比例，重連前仍保有分配權；(c) 退還該座位對未完成魚的投入成本 |
| 斷線發生在進行中的 BOSS 關卡 | BOSS 關卡是否為一個需要完成的單元 | 若 BOSS 有階段性獎勵，需定義未完成階段的處理；若無，則同一般魚 |
| 場景重置（arena reset）時仍有受傷的魚 | 這是**損失項**，必須記錄 | 重置即視為離場，記錄剩餘生命值與各座位已投入成本 |
| 優雅停機（維護或緊急下線） | 停機順序 | 結算所有已完成捕獲 → 退還未完成捕獲的已投入成本 → 記錄魚群狀態與離場 → 對玩家顯示明確原因 → 記錄授權者 |

⚠️ **無論選哪個選項，必須有明文規則且在玩家規則中揭露。** 沒有規則就是事故發生時的爭議來源，且「依當時工程判斷處理」在稽核中無法通過。修改此規則是第 3 類變更（改變期望值且改變揭露內容）。

### 3.2 未完成局不能是「回滾整段時間」

魚機的桌次是共享的：一個座位斷線的 15 秒內，其他 7 個座位仍在正常遊戲並產生真實賠付。**不能以回滾桌次時間來處理單一座位的斷線。** 處理範圍只能是該座位的未完成投入，其他座位的已完成交易不可撤銷。

這與老虎機的差異必須在事故處理流程中明確：完整流程見 `incident-malfunction-handling.md`。

## 4. 上下分與錢包幂等性

### 4.1 兩個幂等鍵

魚機的錢包操作頻率遠高於老虎機（每秒每座位數發子彈，而非每數秒一次 spin），這使幂等性從「好習慣」變成「必要條件」。

| 操作 | 幂等鍵 | 說明 |
|------|--------|------|
| 扣款（發射一發子彈） | `bulletId` | 由伺服器產生，全域唯一。重試同一 `bulletId` 必須不重複扣款 |
| 入帳（一次捕獲的賠付） | `captureId` | 由伺服器產生。重試同一 `captureId` 必須不重複入帳 |

`bulletId` 同時是稽核日誌的主鍵與傷害歸屬紀錄的引用鍵（見 `multiplayer-fairness.md` 第 2.1 節）。用它作為扣款幂等鍵可讓「這筆扣款對應哪一發子彈、那一發打中了什麼」變成單次查詢，而不是跨表推論。

### 4.2 多座位結算的原子性問題

在共享魚池模型 B（依投入成本比例分配賠付）之下，**一次捕獲會同時對多個座位入帳**。這裡有一個老虎機完全沒有的要求：

⚠️ **整筆分配必須是單一原子交易。** 不可對每個座位各發一次入帳請求。

若逐座位入帳：

| 失敗點 | 後果 |
|--------|------|
| 第 3 個座位入帳後系統崩潰 | 前 3 座位已收款、後 5 座位未收款，且無法判斷此 `captureId` 是否「已處理」 |
| 部分座位入帳失敗並重試 | 重試邏輯需追蹤逐座位狀態，複雜度爆增且容易出現重複入帳 |
| 帳務對帳 | 該筆捕獲的賠付總額與魚的賠率倍數不符，觸發偽陽性的 RTP 偏離告警 |

正確做法：以 `captureId` 為幂等鍵，把逐座位的分配明細作為單一交易的內容提交。若錢包服務不支援多帳戶原子交易，則必須在遊戲伺服器與錢包之間引入具備補償機制的交易協調層，且未完成的分配狀態必須持久化，不可只存在記憶體中。

### 4.3 捨入餘數

模型 B 的分配會產生捨入餘數。餘數歸屬規則必須是確定性的（例如給最後一擊者），且各座位賠付總和必須精確等於應付總額。這是數學規則不是實作細節，修改它是第 3 類變更。

### 4.4 機台上下分的系統層對應

實體機台的上下分（實體鑰匙授權、操作者身分記錄、前後餘額）要求見 `cabinet-hardware-compliance.md` 第 3.1 節。混合部署時，機台上下分與線上錢包若共用同一玩家帳戶，兩條路徑的交易必須進入同一本帳並可對帳，否則帳務落差無法歸因。

## 5. 對局重播：魚機的 game recall

### 5.1 為何靜態日誌不夠

老虎機的 game recall 是保存最近 N 次 spin 的靜態欄位（投注額、結果符號、賠付）。魚機的爭議形態不同：「那條魚到底是誰打死的」「我打了半天別人搶走」「這條魚打不死一定有問題」。這三類爭議都需要**時間序列**，靜態欄位無法回答。見 `multiplayer-fairness.md` 第 2.2 節。

### 5.2 重播的組成

對局重播是把桌次的一段時間窗完整重現，需要：

| 元件 | 內容 |
|------|------|
| spawn seed | 該桌魚群生成與路徑排程的隨機來源，使魚群可被完整重建 |
| 事件流 | 逐 tick 的座位事件（發射、砲倍切換、道具使用、進出座位）與伺服器判定結果 |
| 配置引用 | 當時生效的 `buildHash`、`configHash`、PAR sheet 版本 |
| 判定隨機位元 | 每發子彈的判定所消耗的隨機位元（或其可重建的引用） |

### 5.3 硬要求：逐位元相同

⚠️ **重播必須逐位元相同（bit-exact）。** 以同一 spawn seed 與同一事件流重播，逐發子彈的判定結果與逐條魚的結局必須與原始運行完全一致。

這個要求有兩個用途，第二個常被忽略：

1. **爭議處理與監管檢視**：能出示「這條魚初始生命值 168、逐發傷害如下、最後一擊為 bulletId X」是回應控分懷疑的唯一方式。
2. **變更分類的量測儀器**：修改前後的建置以同一輸入重播，若結果序列有任何一發不同，該變更就不是第 2 類。見 `change-management-recert.md` 第 2.1 節。

達成逐位元相同的工程約束：

- 判定路徑不得依賴浮點運算的平台差異。若使用浮點，需固定運算順序並避免依賴編譯器優化層級；判定關鍵路徑建議使用定點或整數運算。
- 判定不得依賴 wall-clock 時間、執行緒調度順序、雜湊表迭代順序或未排序集合的遍歷次序。
- 平行化（多執行緒處理同 tick 的多座位事件）必須有確定性的合併順序。
- 物件池的重用順序不得影響判定（若魚的 ID 由池的重用順序決定，則池行為變成判定輸入）。

### 5.4 重播工具

重播能力必須有可用的工具介面，不能只是「理論上可以重建」：

| 使用者 | 需要的能力 |
|--------|-----------|
| 客服 | 依 `playerId` + 時間或 `captureId` 查出該桌時間窗，視覺化重播並匯出傷害歸屬明細 |
| 稽核／監管 | 依桌次與時間窗匯出完整事件流與配置雜湊，並可獨立驗算 |
| 工程 | 從歷史資料重播到新建置，用於變更分類比對 |

重播資料同時是個人資料，其分類、保存期與刪除要求見 `data-protection-privacy.md`。**博彩監管的長期保存義務與資料最小化要求在重播資料上直接衝突**，這是需要事前處理的設計決定，不是上線後的合規補救。

## 6. 軟體完整性驗證

| 要求 | 實作 |
|------|------|
| 建置雜湊 | 遊戲伺服器二進位與判定模組的雜湊 |
| 配置雜湊 | 數學配置（魚種賠率、生命值分佈、生成權重、砲倍矩陣、tick 頻率）的雜湊 |
| 啟動時驗證 | 雜湊不在已認證組合清單中即**拒絕啟動** |
| 運行期定期重驗 | 失敗則停止接受發射請求並進入故障狀態 |
| 現場可讀 | 雜湊與生效組態編號可由稽核人員讀取而不需開發工具 |

「拒絕啟動」而非「記錄並繼續」是硬要求：後者的實際效果是把未認證建置放進產線並產生真實玩家交易。完整的綁定關係與啟動檢查矩陣見 `change-management-recert.md` 第 5 節。

## 7. 跨桌獎池控制器

跨桌獎池是獨立的系統元件，且依 Appendix A 的對照落入 GLI-12 範圍。

| 要求 | 說明 |
|------|------|
| 貢獻幂等性 | 每發子彈對獎池的貢獻以 `bulletId` 為幂等鍵。重試不得重複累積 |
| 貢獻比例為常數 | 抽取比例不得依營收或玩家歷史變動，見 `payout-control-integrity.md` |
| 必中上限揭露 | 若有 must-hit ceiling，必須在 PAR sheet 明示並計入 RTP |
| 獎池狀態持久化 | 獎池金額不可只存在記憶體；崩潰後必須可精確復原 |
| 觸發的原子性 | 觸發、重設、入帳必須是單一交易 |
| 獎池與基礎遊戲的 RTP 分配 | 獎池是新的數學配置，不是一個開關。加入或移除獎池是第 3 類重大變更 |

### 7.1 絕對不可跨市場或跨數學配置共池

⚠️ **不得把法律地位不同或已認證數學不同的市場玩家放進同一個獎池。** 理由：

| 問題 | 後果 |
|------|------|
| 法律地位不同 | 一個市場的合法玩家與另一個市場的非法部署共享獎金池，使非法收入進入合法帳務 |
| 已認證數學不同 | 各市場的獎池貢獻率與 RTP 分配不同，共池後任一市場的實際 RTP 都不再等於其 PAR sheet 值 |
| 資料落地要求不同 | 見第 9 節 |
| 幣別與匯率 | 跨幣別共池的匯率風險會使獎池的實際期望值浮動，破壞 RTP 固定性 |

正確架構是**依市場分池**，每池有自己的配置、雜湊與 PAR sheet。市場差異矩陣見 `jurisdiction-matrix.md`。

## 8. 監管機關中央系統整合

| 系統 | 市場 | 義務層級 |
|------|------|----------|
| Spelpaus（https://www.spelpaus.se/） | 瑞典 | 持瑞典牌照的營運商必須整合 |
| GamStop（https://www.gamstop.co.uk/） | 英國 | 持 UKGC 牌照的線上營運商必須整合 |

**這兩者是營運商層級的義務，不是遊戲供應商層級的義務。** 對遊戲層的實際影響是：自我排除狀態必須在**發射請求被接受之前**被檢查，而不是在結算時。實作要點與自動發射的授權撤銷問題見 `responsible-gaming.md`。

⚠️ 魚機作為一種遊戲類型是否有額外的中央系統整合要求（例如某些市場對遊戲層事件的即時上報）標記 `UNVERIFIED`。查證路徑：向目標市場監管機關以書面技術問答確認「real-time shared-state multiplayer 遊戲的事件上報粒度是每發子彈、每次捕獲，還是每個 session」。這個問題的答案會直接改變稽核日誌的上報架構，因此必須在架構定案前取得，見 `certification-prep.md` 第 5 節。

## 9. 稽核日誌基礎設施與容量

### 9.1 為何魚機的日誌量是一個架構問題

老虎機每次 spin 產生一筆紀錄。魚機每發子彈產生一筆紀錄，而每個座位每秒可發射數發。

以 8 座位桌、每座位每秒 5 發為例：

| 指標 | 估算 |
|------|------|
| 每桌每秒紀錄數 | 8 × 5 = 約 40 筆／秒 |
| 每桌每小時資料量（約 400 bytes／筆） | 約 55 MB |
| 100 桌每日資料量 | 約 130 GB |
| 100 桌每年（未壓縮、未計索引） | 約 47 TB |

這些是**規模示意估算**，實際值依欄位設計與壓縮率而異，應以自身欄位結構實測。但量級的結論是穩健的：**保存期 × 資料量 = 真實成本**，且這個成本必須在架構階段估算，不是在上線後發現儲存帳單時才處理。

### 9.2 工程後果

| 決定 | 建議 |
|------|------|
| 熱／冷分層 | 近期資料（客服查詢窗口）置於可查詢儲存；長期保存置於低成本歸檔，但必須可在監管要求的時限內取回 |
| 寫入路徑 | 日誌寫入不得阻塞判定 tick。使用非阻塞緩衝，但緩衝遺失即為稽核缺口，故需持久化緩衝而非純記憶體佇列 |
| 唯附加 | 稽核紀錄不可就地修改或刪除 |
| 保存期 | 依各市場要求，見 `jurisdiction-matrix.md`。多市場產品取最長者，或依市場分區保存 |
| 與重播的關係 | 重播所需的事件流是稽核日誌的子集或同一份資料；**不要建兩套** |
| 刪除義務衝突 | 資料主體刪除請求與監管保存義務衝突，處理方式見 `data-protection-privacy.md` |

### 9.3 容量估算應是階段一的輸入

顧問應在需求釐清階段就要求「預計桌數 × 座位數 × 平均射速 × 保存期」四項數字，並當場算出量級。這個數字經常改變客戶對部署拓撲與預算的決定，而它在後期才出現時通常導致縮短保存期的提議——而保存期是監管要求，不是可協商的成本項。

## 10. 資料落地與部署拓撲

| 市場 | 要求 | 信心 |
|------|------|------|
| 巴西 | Law 14.790/2023 下的線上娛樂場要求**巴西境內資料中心**、巴西法人、`.bet.br` 網域，並以葡萄牙文提交認證（https://www.gov.br/fazenda/pt-br/composicao/orgaos/secretaria-de-premios-e-apostas） | `HIGH` 就上述要素而言；魚機是否被歸入可供應的遊戲類型為 `UNVERIFIED`，須向 SPA 確認 |
| 其他市場 | 各市場的資料落地與跨境傳輸要求 | `UNVERIFIED`，依 `jurisdiction-matrix.md` 的查證 SOP 取得 |

### 10.1 資料落地的連鎖後果

資料落地不只是「把資料庫放在境內」。對魚機而言它有一個特有的連鎖效應：

**境內資料中心要求 + 桌是不可分割的親和單位 = 該市場的桌次必須在境內運行 = 該市場的獎池必須與其他市場分離。**

理由：跨桌獎池需要一個權威的獎池狀態，若獎池橫跨兩個資料落地區域，則獎池狀態必然存在於其中一方，另一方的玩家交易資料就離境了。這與第 7.1 節的分池結論一致，但推導路徑不同——即使兩個市場的法律地位與數學配置完全相同，資料落地要求本身就足以強制分池。

### 10.2 部署拓撲的最小結構

| 元件 | 落地約束 |
|------|----------|
| 遊戲伺服器（桌次權威） | 隨市場落地 |
| 錢包與交易紀錄 | 隨市場落地 |
| 稽核日誌與重播資料 | 隨市場落地 |
| 跨桌獎池控制器 | 依市場分離部署 |
| 個人化／分析層（不影響判定） | 可集中，但需符合跨境傳輸規則 |
| 建置與配置發布管線 | 可集中，但各市場的已認證組合清單須分離 |

## 11. 平台層檢查清單

1. 桌次有明確的節點親和映射，節點失效時的桌次處理規則已定義
2. tick 頻率為配置值並納入 configHash，不隨負載自適應
3. tick 超時有事件記錄與告警
4. 判定路徑的輸入集不含客戶端時間戳、客戶端結果或玩家累積統計
5. 斷線／BOSS 中斷／場景重置／優雅停機四種情境皆有明文規則並已揭露
6. 扣款以 `bulletId`、入帳以 `captureId` 為幂等鍵
7. 模型 B 的多座位分配為單一原子交易，捨入規則確定
8. 對局重播已實作且經驗證逐位元相同
9. 重播工具對客服、稽核與工程三種使用者皆可用
10. 判定路徑無浮點平台差異、無執行緒順序依賴、無未排序集合遍歷依賴
11. 建置與配置雜湊於啟動與運行期驗證，不符即拒絕啟動
12. 獎池貢獻幂等、狀態持久化、觸發原子化，且依市場分池
13. 自我排除檢查發生在發射請求被接受之前
14. 稽核日誌容量已估算，熱／冷分層與保存期已依市場確定
15. 日誌寫入不阻塞判定 tick，且緩衝為持久化而非純記憶體
16. 資料落地要求已確認，且其對獎池分離的連鎖後果已納入拓撲設計

## 需要主動說出的事

1. **魚機伺服器不是老虎機 RGS。** 它是持續運行的權威世界，桌是不可分割的親和單位，無狀態隨機分派的拓撲不適用。
2. **tick 頻率是已認證的數學參數。** 為了效能而調 tick 率或改變請求合併方式是第 3 類變更，不是效能調校；因此也不得在高負載時降低 tick 率——負載保護的正確做法是限制每節點桌數或拒絕開新桌。
3. **模型 B 的一次捕獲會同時對多座位入帳，整筆分配必須是單一原子交易。** 逐座位入帳在部分失敗時無法判斷該 `captureId` 是否已處理。
4. **對局重播必須逐位元相同**，否則它既不能處理爭議，也不能當變更分類的量測儀器。浮點運算、執行緒順序與物件池重用順序都是常見的破壞來源。
5. **重播資料與稽核日誌不要建兩套。** 重播所需的事件流就是稽核日誌。
6. **稽核日誌量級是架構問題。** 8 座位桌每秒約 40 筆、每桌每小時約 55 MB、100 桌每日約 130 GB。保存期乘資料量等於真實成本，必須在階段一估算。
7. **不得跨市場共池。** 法律地位、已認證數學、資料落地與幣別任一不同即必須分池；資料落地要求單獨就足以強制分池。
8. **斷線座位的累積傷害處理必須有明文規則並揭露。** 而且不能用回滾桌次時間來處理，因為其他座位的交易已完成且不可撤銷。
9. **Spelpaus 與 GamStop 是營運商層義務**，但它們對遊戲層的具體後果是自我排除必須在發射請求被接受之前檢查；魚機是否另有遊戲層即時上報要求為 `UNVERIFIED`，須以書面技術問答確認且應在架構定案前完成。
