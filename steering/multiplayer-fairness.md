# 多人同桌公平性指引

本指引涵蓋共享魚池的傷害歸屬模型、搶魚與最後一擊判定、延遲補償與伺服器權威、座位間公平性驗證、共謀洗分偵測，以及可稽核性設計。

多人同桌是魚機與老虎機最根本的結構差異。老虎機的每個玩家在自己的機率空間中獨立運作；魚機的 8 個座位共享同一批魚，一個座位的行動直接改變其他座位的機會。這產生了老虎機領域完全不存在的公平性、可稽核性與反共謀問題。

---

## 1. 共享魚池的三種模型

### 1.1 模型比較

| 模型 | 機制 | 傷害歸屬問題 | 常見度 |
|------|------|--------------|--------|
| A：完全共享 | 所有座位扣減同一份生命值，最後一擊者獲得全額賠付 | 嚴重（搶魚） | 業界最常見 |
| B：共享生命值 + 傷害比例分配 | 所有座位扣減同一份生命值，賠付依傷害佔比分配 | 中等（需精確歸屬） | 較公平但體感較弱 |
| C：獨立進度 | 每個座位對每條魚有獨立生命值進度，視覺共享但機制獨立 | 無 | 較少，但合規最單純 |

### 1.2 模型 A 的問題

模型 A 的「最後一擊拿全部」設計製造了明確的搶魚動機，也製造了三個難題：

1. **玩家 X 打掉一條 ×150 金龍 95% 的生命值，玩家 Y 補最後一發拿走全部賠付。** X 的投入完全無回收。這在體感上是不公平的，但它是規則。
2. **X 的期望值依賴 Y 的行為。** 這使個別座位的 RTP 不是遊戲配置的固定屬性，而是同桌組成的函式。必須在 `math-verification.md` 的多人情境分析中量化並揭露。
3. **爭議無法用單筆日誌回答。** 玩家申訴「那條魚是我打的」時，必須能重播該魚的完整傷害歷程。

**採用模型 A 是合法設計，但必須：** 在玩家規則中明示最後一擊規則、在 PAR sheet 揭露座位間期望值依賴、在稽核層保存完整傷害歸屬。

### 1.3 模型 B 的實作要點

依傷害佔比分配賠付較公平，但引入精度問題：

```
座位 s 的賠付 = 賠率倍數 × 座位 s 的累積傷害佔比 × 該座位射擊時的加權砲倍
```

**砲倍加權是關鍵。** 若不加權，用 ×1 砲打 50% 傷害的玩家與用 ×100 砲打 50% 傷害的玩家獲得相同賠付，這破壞了「賠付與投注成比例」的基本原則，且會造成各砲倍 RTP 不一致（見 `math-model.md`）。

正確做法是以**投入成本**而非傷害量作為分配基準：

```
座位 s 的賠付 = 賠率倍數 × (座位 s 對該魚的投入成本 / 該魚的總投入成本) × 該魚的總投入成本 / 基準砲倍
```

實作時必須處理浮點誤差與捨入：所有座位的賠付總和必須精確等於應付總額，餘數的處理規則必須是確定性的（例如給最後一擊者），且必須揭露。

### 1.4 模型 C 的權衡

獨立進度完全消除傷害歸屬問題，合規最單純，各座位 RTP 完全獨立於同桌組成。代價是同桌互動的體感消失——玩家看到別人在打同一條魚但打不死，容易被認為是視覺欺騙。

**若採用模型 C，玩家規則必須明示「各玩家的傷害進度獨立」**，否則構成誤導呈現，這在英國 UKGC 的「呈現」判準下是實質風險（見 `skill-chance-classification.md`）。

## 2. 傷害歸屬的可稽核性

### 2.1 必須記錄的資料

每條魚在被擊殺或離場時，必須有完整的傷害歸屬紀錄：

```
fishId
物種與賠率倍數
初始生命值
傷害事件序列：[
  { bulletId, seatId, playerId, betMultiplier, damage, hpAfter, serverTick }
  ...
]
結局：captured | escaped | scene_reset | round_end
若 captured：killingBulletId、賠付分配明細（逐座位）
若 escaped：剩餘生命值、各座位已投入成本
```

### 2.2 為什麼不能只記錄最後一擊

只記錄最後一擊的系統無法回答魚機最常見的三類爭議：

| 爭議 | 需要的資料 |
|------|-----------|
| 「那條魚是我打死的」 | 完整傷害序列與 `killingBulletId` |
| 「我打了半天別人搶走」 | 各座位投入成本，證明規則被正確套用 |
| 「這條魚打不死一定有問題」 | 初始生命值、逐發傷害、以及該魚種生命值分佈的配置值 |

第三類爭議尤其重要，因為它同時是玩家對控分的懷疑。能夠出示「這條魚初始生命值 168，符合金龍的固定分佈，逐發傷害如下」的紀錄，是回應該懷疑的唯一方式。

### 2.3 離場魚也必須記錄

已被扣血但游出畫面的魚，其紀錄同樣必要。理由：玩家爭議、`math-verification.md` 的損失項驗證、以及偵測異常的魚離場率（可能指示彈道或碰撞判定的實作錯誤）。

## 3. 延遲補償與伺服器權威

### 3.1 核心衝突

魚機是即時遊戲，玩家瞄準移動目標。若判定完全依伺服器接收到請求時的世界狀態，則高延遲玩家會系統性打不中——瞄準時魚在 A 點，伺服器處理時魚已到 B 點。這是實質的座位間不公平，且不公平程度依網路品質而定。

但若採用 FPS 遊戲常見的「回溯（lag compensation）」——伺服器回溯到客戶端發射時的世界狀態進行判定——則客戶端聲稱的時間戳成為判定輸入，這是可被操縱的攻擊面。

### 3.2 建議做法

| 措施 | 說明 |
|------|------|
| 伺服器產生所有時間戳 | 客戶端提交的時間僅作為參考與異常偵測，不直接用於判定 |
| 有界回溯 | 允許回溯，但上限為伺服器量測的該連線 RTT 的一半，且設絕對上限（例如 150 ms） |
| RTT 由伺服器量測 | 不接受客戶端申報的延遲 |
| 子彈飛行時間吸收延遲 | 設計上讓子彈有可見的飛行時間（例如 300–500 ms），使正常網路波動落在飛行時間內，大幅減少回溯需求 |
| 命中判定用膠囊而非點 | 對魚體與子彈使用有體積的碰撞形狀，容忍小幅位置誤差 |
| 記錄回溯量 | 每發子彈的稽核日誌記錄實際使用的回溯毫秒數，供事後分析與異常偵測 |

**子彈飛行時間是魚機的天然優勢。** 老虎機沒有這個緩衝，FPS 遊戲的子彈通常是瞬時的；魚機的子彈本來就慢，把它設計成延遲吸收機制既符合遊戲感也解決公平性問題。

### 3.3 客戶端預測與回滾

客戶端可以預測命中並播放特效，但伺服器結果必須覆蓋。回滾的體感處理：

| 情境 | 建議處理 |
|------|----------|
| 客戶端預測命中，伺服器判定未命中 | 播放「擦過」動畫，不顯示傷害數字。避免「命中特效後魚滿血」的明顯矛盾 |
| 客戶端預測未捕獲，伺服器判定捕獲 | 延遲播放捕獲動畫，體感上可接受 |
| 客戶端預測捕獲，伺服器判定被其他座位搶先 | 播放「被搶走」的明確回饋，並顯示搶走的座位。**隱藏這件事會製造申訴** |
| 大幅狀態不同步（重連後） | 完整重新同步該桌狀態，不嘗試漸進修正 |

第三項是魚機特有且重要的體驗設計：**搶魚必須被明確呈現，不能靜默處理。** 玩家看到「座位 3 搶走了」會抱怨規則，但看到魚無聲消失會懷疑機台作假。前者是設計爭議，後者是誠信爭議。

### 3.4 「客戶端判定 + 伺服器驗證」不可接受

若伺服器僅檢查客戶端上報結果是否落在合理範圍，攻擊者可在合理範圍內持續選擇對自己最有利的結果。判定必須由伺服器產生，見 `rng-capture-determination.md` 第 3.1 節。

## 4. 座位間公平性驗證

### 4.1 需要驗證的項目

| 項目 | 驗證方法 | 通過標準 |
|------|----------|----------|
| 魚群入場方向分佈 | 長期統計各方向入場比例 | 各方向均衡，或至少不長期偏向特定座位 |
| 各座位到魚群的幾何距離 | 分析桌型與生成區域 | 各座位的平均可及範圍相當 |
| 各座位的實測 RTP | 相同策略代理人置於不同座位，長期模擬 | 各座位 RTP 差異在統計誤差內 |
| 各座位的命中率 | 同上 | 差異在統計誤差內 |
| BOSS 關卡的座位可及性 | BOSS 出現位置與各座位的距離分析 | 無座位系統性有利 |

### 4.2 常見的座位不公平來源

| 來源 | 說明 |
|------|------|
| 魚群固定從左側入場 | 左側座位先接觸魚群，有先手優勢 |
| 桌型為長方形 | 長邊座位的可及範圍大於短邊座位 |
| BOSS 固定出現在畫面中央上方 | 上方座位距離較近 |
| 特殊武器的方向性 | 雷射沿發射方向貫穿，某些座位的貫穿路徑覆蓋較多魚 |
| 客戶端解析度差異 | 線上桌若各客戶端可視範圍不同，構成資訊不對稱 |

最後一項在線上魚機特別容易發生：不同螢幕比例的玩家看到的畫面範圍不同。**必須確保所有座位的可視資訊完全相同**（以裁切或加黑邊處理，而非擴大視野），否則構成資訊不對稱。

### 4.3 實體機台的額外項目

實體機台的座位公平性還包含硬體層：觸控靈敏度、按鍵手感、螢幕視角。這些屬硬體驗收項目，見 `cabinet-hardware-compliance.md`。

## 5. 共謀與價值轉移偵測

### 5.1 魚機特有的洗分風險

同桌結構讓兩個帳號可以在不觸發傳統博彩反洗錢規則的情況下移轉價值。這是魚機在線上真錢環境中的核心 AML 風險，且老虎機完全沒有對應形態。

| 手法 | 機制 |
|------|------|
| 讓分（模型 A 下） | A 帳號把大魚打到將死，B 帳號補最後一擊拿走賠付。價值從 A 移到 B |
| 包桌操作 | 一組帳號佔滿整桌，排除其他玩家，內部控制價值流向 |
| 高砲倍傾倒 | A 以極高砲倍在低期望情境持續發射，B 收割，形成單向價值流 |
| 獎池套利 | 一組帳號協同衝擊跨桌獎池的必中上限 |

### 5.2 偵測訊號

| 訊號 | 說明 |
|------|------|
| 座位共現率異常 | 兩個帳號同桌的頻率遠高於隨機預期 |
| 單向賠付流 | 帳號對之間的「最後一擊搶奪」呈現高度單向性 |
| 讓分模式 | 某帳號持續在魚將死時停止射擊 |
| 極端 RTP 分歧 | 同桌帳號中一方 RTP 極低、一方極高，且持續 |
| 註冊與金流關聯 | 相同支付工具、裝置指紋、IP 段 |
| 包桌行為 | 一組帳號同時進入且填滿新開桌次的頻率 |

「某帳號持續在魚將死時停止射擊」是最強的單一訊號，因為它與任何理性的個人玩法都相反。

### 5.3 實作要求

- 座位共現分析必須是常態監控，不是事後查案工具。
- 偵測邏輯應在遊戲伺服器之外的分析層執行，避免影響判定路徑效能。
- 偵測結果不得回饋到捕獲判定（那會構成依玩家歷史調整結果，見 `payout-control-integrity.md`）。處置方式是帳戶層行動，不是遊戲層調整。
- 完整的帳戶處置流程見 `aml-kyc-player-account.md`。

## 6. 同桌事故的特殊處理

多人同桌讓事故的影響範圍與處理複雜度都放大。

| 事故 | 特殊考量 |
|------|----------|
| 桌次崩潰 | 所有座位的未完成狀態需一致處理；不可只補償申訴者 |
| 賠付分配錯誤（模型 B） | 需重算全部受影響座位，可能包含已離桌玩家 |
| 傷害歸屬錯判 | 錯誤的最後一擊判定同時造成一方多得、一方少得 |
| 單一座位斷線 | 該座位已投入的傷害如何處理必須有明確規則並揭露 |
| 魚群狀態不同步 | 各客戶端顯示不同，需判斷權威狀態並全桌重新同步 |

**單一座位斷線時已投入傷害的處理規則必須事先定義並在玩家規則中揭露。** 常見選項：保留傷害（魚維持受傷狀態，其他座位可撿現成）、或該座位重連後仍可繼續。無論選哪個，不能沒有規則。

完整的事故處理流程見 `incident-malfunction-handling.md`。

## 7. 設計檢查清單

1. 已明確選定共享模型（A／B／C）並在玩家規則中揭露
2. 模型 B 的分配以投入成本為基準，且捨入規則確定並揭露
3. 每條魚的完整傷害序列與結局都被記錄，含離場魚
4. 所有判定在伺服器端；客戶端僅預測
5. 回溯有上限，RTT 由伺服器量測，回溯量記入日誌
6. 子彈飛行時間足以吸收正常網路波動
7. 搶魚被明確呈現，不靜默處理
8. 各座位可視資訊完全相同
9. 各座位 RTP 與命中率經模擬驗證無系統性差異
10. 座位共現與單向賠付流的監控已上線
11. 斷線時已投入傷害的處理規則已定義並揭露
12. 座位間期望值依賴已在 PAR sheet 揭露

## 8. 需要主動說出的事

1. **模型 A 下個別座位的 RTP 依賴同桌組成。** 這必須量化並揭露，是實驗室會問的問題。
2. **模型 B 必須以投入成本分配，不是傷害量。** 以傷害量分配會造成各砲倍 RTP 不一致。
3. **搶魚必須明確呈現。** 靜默處理會把設計爭議升級為誠信爭議。
4. **只記錄最後一擊的系統無法處理魚機的主要爭議類型。**
5. **同桌讓分是魚機獨有的洗錢管道**，且不會被傳統博彩 AML 規則捕捉到。
6. **偵測結果不得回饋到遊戲判定。** 處置在帳戶層，不在遊戲層。
7. **不同螢幕比例造成的可視範圍差異是資訊不對稱**，必須以裁切處理。
8. **斷線座位的已投入傷害必須有明文規則。** 沒有規則就是事故發生時的爭議來源。
