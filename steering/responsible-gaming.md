# 負責任遊戲實作指引

本指引涵蓋魚機的負責任遊戲功能實作：為何魚機的結構性風險高於老虎機、自動發射與連續投入管控、砲倍升幅風險、沉浸與時間流逝、同桌社會壓力、限額與自我排除的實作層級、年齡分級，以及設計檢查清單。

---

## 1. 魚機的結構性風險為何高於老虎機

這一節是整份指引的前提。若把老虎機的負責任遊戲功能清單直接搬到魚機上，會漏掉魚機的主要風險來源，因為那些風險不在「每次投注」這個層次，而在「投注的節奏由誰決定」這個層次。

| 風險維度 | 老虎機 | 魚機 |
|----------|--------|------|
| 決策點 | 每次 spin 一個明確的按下動作 | **沒有**。按住發射即持續投注 |
| 投入速度決定者 | 遊戲循環（每次 spin 的完成） | **玩家射速**，可持續且無循環邊界 |
| 投注額變更 | 明確的下注操作 | 砲倍切換，一次點擊可改變數十倍投入速度 |
| 自然中斷點 | 每次 spin 結束是天然的停頓 | 場景連續輪替，無停頓 |
| 社會情境 | 單人 | 同桌可見他人輸贏，有觀察與比較壓力 |
| 損失可見性 | 每次 spin 的結果明確 | 多發子彈才換一次捕獲，投入與結果的因果被稀釋 |

### 1.1 沒有離散決策點，這是魚機最根本的問題

老虎機的每一次投注都對應一個玩家的主動動作，因此每次投注都是一個可以停下來的時刻。魚機不是：**玩家按住發射鍵，子彈以固定射速連續射出，每一發都是一次扣款。** 玩家的一個動作對應數十次扣款。

工程後果：**負責任遊戲的干預點不能設計在「每次投注前」，因為那個時刻不存在。** 干預點必須是時間或累積金額觸發，而非事件觸發。

| 干預設計 | 老虎機適用 | 魚機適用 |
|----------|-----------|----------|
| 每次投注前顯示餘額 | ✅ | ⚠️ 無效，因為玩家不會逐發看 |
| 每 N 次投注顯示提示 | ✅ | ⚠️ N 發子彈在數秒內就達成，會變成干擾而被忽略 |
| 每 N 分鐘顯示累積淨勝負 | ✅ | ✅ **這是魚機的主要干預形式** |
| 累積投入達門檻時中斷 | ✅ | ✅ 必要 |
| 錢包層限額 | ✅ | ✅ 必要且優先 |

### 1.2 投入速度的量級

以 5 發／秒的射速為例（單機實測值依專案而異）：

| 砲倍 | 每秒投入（以 ×1 彈值為單位） | 每分鐘投入 |
|------|------------------------------|------------|
| ×1 | 5 | 300 |
| ×10 | 50 | 3,000 |
| ×100 | 500 | 30,000 |

⚠️ **從 ×1 切到 ×100 是一次點擊，投入速度變成 100 倍。** 這是魚機獨有的風險：老虎機要把投注額提高 100 倍需要明確的下注操作，且下一次 spin 才生效；魚機的砲倍切換即時生效於下一發子彈，而下一發在 200 毫秒內。

## 2. 自動發射（Auto-fire）

### 2.1 自動發射移除了最後一個決策點

自動發射是魚機的 autoplay 對應物，但它比 autoplay 更徹底：autoplay 至少有「玩幾局」的設定作為邊界，自動發射通常是「開啟後持續發射直到關閉或餘額耗盡」。

**按住發射鍵時，玩家的手仍在裝置上，仍有一個持續的身體動作作為投入的感知錨點。自動發射把這個錨點也移除了。** 玩家可以離開座位、看手機、與旁人交談，而扣款持續進行。

### 2.2 規範狀態

| 事項 | 信心 |
|------|------|
| 英國對線上老虎機（slots）禁止 autoplay | `MEDIUM`。此為 UKGC 遠端技術標準（RTS）下的要求，查證路徑：向 UKGC 取得現行 RTS 文本並確認條號與適用範圍（https://www.gamblingcommission.gov.uk/） |
| 該禁止是否適用於魚機／捕魚類遊戲 | ⚠️ `UNVERIFIED`。魚機不是 slots，且「自動發射」與「autoplay」的定義對應關係未經確認。查證路徑：以書面技術問答向 UKGC 確認「連續射擊型遊戲的自動發射是否落入 autoplay 相關要求」，並保留書面回覆 |
| 其他市場對自動發射的立場 | `UNVERIFIED`，依 `jurisdiction-matrix.md` 的查證 SOP 逐市場取得 |

**顧問不應斷言「英國禁止自動發射」，也不應斷言「魚機不受此限」。** 正確的輸出是：這是一個必須以書面確認的爭點，且它的答案會改變核心遊戲操作方式，因此必須在遊戲操作設計定案前確認。

### 2.3 建議的自動發射管控（不論市場要求為何）

| 措施 | 說明 |
|------|------|
| 明確的上限 | 以發數、時間或累積投入為上限，達到即停止並要求重新啟動 |
| 顯示已投入 | 自動發射期間持續顯示本次自動發射的累積投入與淨勝負 |
| 任何狀態變更即停止 | 砲倍變更、餘額低於門檻、限額接近、場景重置皆停止 |
| **狀態變更時撤銷授權** | 見第 5.3 節 |
| 不得在自動發射期間切換砲倍 | 避免無感知的投入速度躍升 |

## 3. 砲倍升幅管控

砲倍是魚機的投注額，且它的切換成本比老虎機的下注操作低得多。

| 措施 | 說明 |
|------|------|
| 大幅升檔需明確確認 | 跨越設定倍數（例如超過當前砲倍的 5 倍）時要求二次確認，並顯示新的每分鐘投入估算 |
| 顯示投入速度而非僅顯示彈值 | 「×100，約每分鐘 30,000」比「×100」有意義得多 |
| 單場砲倍上限 | 考慮提供玩家自設的單場最高砲倍，且**降低可即時生效、提高需冷卻期** |
| 自動發射期間鎖定砲倍 | 見第 2.3 節 |
| 砲倍變更事件記入稽核日誌 | 同時是負責任遊戲證據與行為分析輸入 |

「降低即時生效、提高需冷卻」這個非對稱設計是玩家保護的通用形態，也適用於限額（第 5.1 節）。

## 4. 沉浸、時間流逝與社會壓力

### 4.1 場景連續輪替沒有自然中斷點

老虎機的每次 spin 結束是一個微小的停頓，累積起來構成節奏感與時間感。魚機的場景輪替是連續的：一個場景結束、下一個場景的魚群立刻入場，BOSS 關卡更是明確設計為「不要中斷」。

工程後果：**時間感必須由 UI 主動提供，因為遊戲循環不提供。**

| 措施 | 說明 |
|------|------|
| 累積遊戲時間持續可見 | 不是藏在選單裡的統計頁 |
| 定時提醒 | 每 N 分鐘顯示已玩時間與本場累積淨勝負，需要玩家確認才繼續 |
| 場景輪替時的自然插入點 | 若要在不破壞體驗的位置插入提醒，場景切換是唯一的候選 |
| 顯示真實貨幣 | 淨勝負與餘額必須以真實貨幣顯示，不只顯示點數。點數顯示會系統性淡化損失感 |

### 4.2 同桌社會壓力是魚機獨有的風險

| 情境 | 風險 |
|------|------|
| 鄰座以高砲倍打中 ×150 大魚，全桌可見 | 誘發模仿性的砲倍升檔 |
| 全桌一起打 BOSS | 集體行為壓力，離桌的社會成本上升 |
| 包桌（一組人佔滿整桌） | 群體動態使個人的停止決定更困難 |
| 排行榜或座位輸贏排名 | 直接製造比較壓力 |

⚠️ **設計選擇會放大或緩解這個風險。** 具體建議：

- **不要顯示其他座位的累積輸贏或砲倍。** 顯示他人的捕獲是遊戲樂趣的一部分（且搶魚必須被明確呈現，見 `multiplayer-fairness.md` 第 3.3 節），但顯示他人的**累積金額**只有比較壓力的作用。
- **不要設計座位間的輸贏排行榜。**
- BOSS 關卡的集體節奏若無法避免，至少確保離桌不會造成該玩家已投入的損失（斷線傷害處理規則須揭露，見 `platform-systems-compliance.md` 第 3.1 節）。
- 包桌行為同時是共謀訊號，見 `multiplayer-fairness.md` 第 5 節與 `aml-kyc-player-account.md`。

## 5. 限額與自我排除的實作層級

### 5.1 限額必須在錢包層，不在遊戲層

| 限額類型 | 實作層 | 理由 |
|----------|--------|------|
| 存款限額 | 錢包／帳戶 | 遊戲層看不到存款 |
| 單日／單週／單月投入限額 | 錢包 | 玩家可能跨多桌、多款遊戲；遊戲層只知道本桌 |
| 損失限額 | 錢包 | 同上 |
| 單場時間限額 | 遊戲層可執行，但狀態需存於帳戶 | 跨裝置重連時需延續 |
| 單場最高砲倍 | 遊戲層執行，帳戶層儲存 | 屬遊戲參數但是玩家設定 |

⚠️ **在遊戲層實作投入限額的專案，在玩家同時開兩桌時限額會失效。** 這是常見缺陷：限額計數器存在桌次實例中，兩桌各算一份。限額必須是帳戶層的單一權威計數。

限額變更的非對稱規則：**收緊即時生效，放寬需冷卻期。** 冷卻期長度依市場要求，多數市場有明文規定但本 Power 標記 `UNVERIFIED`，須依 `jurisdiction-matrix.md` 查證。

### 5.2 自我排除必須在發射請求被接受之前檢查

自我排除的檢查點是實作上最容易放錯的地方。

⚠️ **檢查必須發生在捕獲判定生命週期的第 1 階段——發射請求受理——之前，不是在結算時。** 見 `rng-capture-determination.md` 的判定生命週期。

若檢查在結算時：

| 問題 | 後果 |
|------|------|
| 已排除玩家的子彈已被扣款 | 需退款，且該子彈已對共享魚池造成傷害，影響其他座位的既成結果 |
| 該子彈已捕獲一條魚 | 賠付要不要給？不給則已扣款無對價；給則違反排除義務 |
| 模型 B 下該子彈已計入分配基準 | 撤銷會改變其他座位的賠付，而那些賠付可能已入帳 |

**魚機的共享狀態使「事後撤銷一發子彈」在數學上無法乾淨完成。** 這是為什麼檢查點必須在受理之前。

國家級自我排除系統：GamStop（英國，https://www.gamstop.co.uk/）、Spelpaus（瑞典，https://www.spelpaus.se/）。整合是營運商層義務，見 `platform-systems-compliance.md` 第 8 節。

### 5.3 自動發射是一個持續有效的授權，必須在狀態變更時撤銷

這是魚機特有且高風險的實作缺口。

自動發射開啟後，發射請求是由客戶端或伺服器的計時器產生的，**不是每一發都對應一次玩家動作**。若自我排除、限額觸及或帳戶凍結發生在自動發射進行中，而系統只在「玩家按下發射」時檢查狀態，則自動發射會繼續。

要求：

| 觸發 | 動作 |
|------|------|
| 玩家進入自我排除名單 | 立即停止自動發射，拒絕後續發射請求，記錄事件 |
| 帳戶被凍結或標記 | 同上 |
| 限額觸及 | 停止自動發射並顯示原因 |
| 年齡驗證狀態失效 | 同上 |
| 任何帳戶狀態機轉換 | 撤銷所有進行中的持續授權 |

實作建議：把自動發射建模為一個**具有明確授權來源的持續授權（standing authorisation）**，其有效性在每一個 tick 被重新檢查，而不是在開啟時檢查一次。帳戶狀態機定義見 `aml-kyc-player-account.md`。

## 6. 年齡分級與入場管控

### 6.1 台灣（信心 `HIGH`）

法源：https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=J0080024

| 條文 | 內容 |
|------|------|
| 第 5 條 | 分普通級與限制級；**限制級僅供 18 歲以上**；同一營業場所不得混合營業級別 |
| 第 17 條第 1 項第 1 款 | 普通級：**禁止未滿 15 歲於上課時間及夜間 10 時以後進入及滯留** |
| 第 17 條第 1 項第 2 款 | 限制級：**禁止未滿 18 歲進入** |
| 第 9 條 | 營業場所應距國中小、高中職、醫院 50 公尺以上 |

第 17 條第 1 項第 1 款的結構值得注意：它不是單純的年齡門檻，而是**年齡加時段加狀態（進入與滯留）**的複合條件。工程後果：若機台或場所系統有會員識別，則「滯留」的持續檢查是必要的，不只是入場時檢查一次；且時段條件意味著系統需要可信的時間來源。此外「上課時間」是外部條件，需可配置（假日、寒暑假），而該配置的正確性是場所業者責任，見 `advisory-engagement.md` 第 3 節的四方責任矩陣。

### 6.2 英國（信心 `HIGH`）

| 類別 | 年齡 | 限額 |
|------|------|------|
| Cat C | 18 歲以上 | 投注上限 £1、獎金上限 £100 |
| Cat D | **無年齡限制** | 限額更低 |

來源：https://www.gamblingcommission.gov.uk/licensees-and-businesses/guide/gaming-machine-categories

⚠️ 魚機常被廠商定位為家庭娛樂中心機台（Cat D 情境），但 Cat D 的限額極低，且該定位的法律代價見 https://www.gov.uk/government/consultations/consultation-on-category-d-gaming-machines-and-licensing-for-bingo-premises/category-d-gaming-machines。**「無年齡限制」不是優勢，它伴隨的是使商業模型難以成立的限額。** 另外，這些限額如何套到「一發子彈」這個原子投注單位上是 `UNVERIFIED`，須以書面技術問答確認，見 `certification-prep.md` 第 5.2 節。

### 6.3 其他市場與線上

線上魚機的最低年齡與身分驗證要求依市場而異，標記 `UNVERIFIED`，見 `jurisdiction-matrix.md`。實作層面的帳戶狀態機與 KYC 流程見 `aml-kyc-player-account.md`。實體機台的入場標示與現場查驗要求見 `cabinet-hardware-compliance.md` 第 6 節。

## 8. 絕對不可跨越的紅線：負責任遊戲功能不得以調整機率實作

⚠️ 這是本指引最重要的一條，也是魚機專案最容易善意違規的地方。

以下做法**全部是補償式控分**，屬架構違規，不是負責任遊戲功能：

| 意圖 | 錯誤做法 | 為何違規 |
|------|----------|----------|
| 保護連續虧損的玩家 | 提高其捕獲機率 | 結果依玩家歷史，違反獨立性 |
| 降低新玩家的挫折感 | 降低新手區魚的生命值 | 依帳齡調整期望值 |
| 減緩高投入玩家的損失速度 | 對高砲倍玩家提高捕獲率 | 各砲倍 RTP 不一致，且依行為調整 |
| 「冷靜期」的軟性實作 | 玩家連續遊戲過久後降低魚的價值 | 依時間調整期望值 |
| 防止玩家一次輸太多 | 累積虧損達門檻時強制捕獲一條大魚 | 保底機制即控分 |

見 `payout-control-integrity.md` 第 2.1 節。

**合規的替代做法一律是在遊戲之外干預，不是在數學之內：**

| 目的 | 合規做法 |
|------|----------|
| 減緩投入速度 | 錢包層限額、單場時間限額、單場砲倍上限 |
| 降低單場最大損失 | 損失限額（錢包層）、砲倍上限 |
| 提高損失感知 | 真實貨幣顯示、定時淨勝負提醒、投入速度顯示 |
| 降低整體波動性 | **在數學模型設計階段**設計低波動配置（降低最高魚種倍數與變異），並各自驗證與送測，見 `math-model.md` |
| 減緩挫折感 | 提高體感命中率、降低稀有事件比重——同樣是固定配置的設計選擇，不是動態調整 |

最後兩項與控分的差別是：**低波動配置是揭露的固定配置並經過驗證；動態調整是隱藏的、依歷史變動的控制器。** 兩者可能達成相近的商業或玩家體驗目的，但一個可以送測，一個不能。

## 9. 設計檢查清單

1. 干預點為時間或累積金額觸發，不是每次投注觸發
2. 累積遊戲時間持續可見，並有需確認的定時提醒
3. 淨勝負與餘額以真實貨幣顯示，不只點數
4. 顯示投入速度（每分鐘估算），不只顯示彈值
5. 大幅砲倍升檔需二次確認並顯示新投入速度
6. 提供玩家自設單場最高砲倍，降低即時生效、提高需冷卻
7. 自動發射有明確上限（發數／時間／累積投入）
8. 自動發射期間不得切換砲倍
9. 自動發射建模為持續授權，其有效性每 tick 重新檢查
10. 任何帳戶狀態轉換立即撤銷自動發射並拒絕後續發射
11. 自我排除檢查發生在發射請求受理之前
12. 限額計數在帳戶層為單一權威，同時開多桌不會失效
13. 限額收緊即時生效、放寬需冷卻期
14. 不顯示其他座位的累積輸贏或砲倍；無座位排行榜
15. 斷線／離桌不造成該玩家已投入傷害的不明損失（規則已揭露）
16. 年齡與時段管控符合市場要求；台灣普通級的「滯留」為持續檢查而非入場一次
17. 求助資源在遊戲內可及，並依市場顯示
18. 沒有任何負責任遊戲功能是以調整捕獲機率、傷害分佈或魚的生命值實作
19. 砲倍變更、自動發射開關、限額觸及、提醒確認皆記入稽核日誌
20. 自動發射的規範適用性已以書面技術問答向目標市場確認

## 需要主動說出的事

1. **魚機沒有離散的投注決策點。** 玩家按住發射鍵，一個動作對應數十次扣款，因此「每次投注前提示」這類老虎機干預在魚機上無效，干預必須是時間或累積金額觸發。
2. **砲倍從 ×1 切到 ×100 是一次點擊，投入速度變成 100 倍。** 這需要二次確認並顯示新的每分鐘投入估算，而不只是顯示新彈值。
3. **自動發射移除了投入的最後一個感知錨點**，且它是一個持續有效的授權——必須每 tick 重新檢查有效性，並在任何帳戶狀態轉換時撤銷。只在開啟時檢查是實務上高頻的缺口。
4. **自我排除必須在發射請求受理之前檢查，不能在結算時。** 因為共享魚池讓「事後撤銷一發子彈」在數學上無法乾淨完成：那發子彈的傷害已影響其他座位的既成結果。
5. **限額若實作在遊戲層，玩家同時開兩桌時會失效。** 限額計數必須是帳戶層的單一權威。
6. **英國對線上老虎機禁止 autoplay（`MEDIUM`），但是否適用於魚機的自動發射是 `UNVERIFIED`。** 這是必須以書面技術問答確認的爭點，且答案會改變核心操作設計，所以要在設計定案前問。
7. **不要顯示其他座位的累積輸贏，也不要做座位排行榜。** 顯示他人的捕獲是遊戲性（且搶魚必須明示），顯示他人的累積金額只有比較壓力的作用。
8. **場景連續輪替沒有自然中斷點，時間感必須由 UI 主動提供。**
9. **⚠️ 負責任遊戲功能絕不可以調整捕獲機率、傷害分佈或魚的生命值來實作。** 那是控分，屬架構違規。合規的替代做法一律在遊戲之外（錢包限額、時間限額、砲倍上限）或在數學設計階段（揭露且經驗證的低波動配置）。
