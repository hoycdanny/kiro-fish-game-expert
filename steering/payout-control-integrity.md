# 派彩控制完整性指引

本指引界定合規的長期 RTP 設計與違規的補償式控分機制之間的紅線。這是魚機專案送測失敗最常見的單一原因，也是本 Power 中最需要主動提出的議題。

---

## 1. 問題陳述

魚機產業長期存在一種派彩控制方式：機台記錄累積投入與累積賠付，當實際回收率低於設定目標時提高捕獲機率，高於目標時降低捕獲機率。業界稱之為場控、控分、機率補償、記憶體控分或抽水控制。

這個做法在娛樂機台市場有其商業邏輯：場所業者需要可預測的日回收，機台廠商以此作為賣點。但在任何受監管的博彩市場，它直接違反遊戲獨立性要求。

**GLI-11 對 gaming device 的界定包含「以隨機性決定獎項」，並要求遊戲結果彼此獨立。** 補償式控分使當前結果依賴先前結果，這不是參數問題，是架構違規。
- GLI-11 v3.0 全文：https://gaminglabs.com/wp-content/uploads/2018/09/GLI-11-Gaming-Devices-V3-0.pdf

## 2. 紅線在哪裡

### 2.1 明確違規

以下任一項存在，即為補償式控分：

| 機制 | 常見說法 |
|------|----------|
| 依累積投入與賠付差額調整捕獲機率 | 「回收率控制」「場控」 |
| 依累積差額調整每發傷害的期望值 | 「難度自動調節」 |
| 依累積差額調整魚群中高倍魚的數量或初始生命值 | 「魚況控制」 |
| 未擊殺的魚將已投入傷害轉記到下一條魚 | 「記血」「不浪費子彈」 |
| 依玩家個人歷史調整其捕獲機率 | 「新手保護」「大戶控制」 |
| 依帳戶餘額或儲值金額調整捕獲機率 | 「VIP 待遇」 |
| 依當日營收目標動態調整 RTP | 「營運調節」 |
| 在特定時段調整捕獲機率 | 「離峰回饋」 |
| 保底機制：連續 N 發未捕獲則強制捕獲 | 「防挫折保護」 |

最後一項需要特別說明，因為它常被誤認為玩家友善的無害設計。**保底機制是條件機率調整，違反獨立性。** 若第 30 發的捕獲機率因為前 29 發失敗而變成 100%，那麼結果依賴歷史，這是明確違規。

### 2.2 允許

以下不構成控分：

| 機制 | 為何允許 |
|------|----------|
| 依該魚當前剩餘生命值決定捕獲 | 生命值是魚的公開規則屬性，不是玩家歷史 |
| 每發傷害從**固定分佈**抽樣 | 分佈參數為常數，不隨任何歷史變動 |
| 確定性場景與 BOSS 排程 | 排程不依玩家行為或營收 |
| 跨桌獎池的固定抽取比例 | 抽取比例為常數 |
| 跨桌獎池的必中上限（must-hit ceiling） | 若在 PAR sheet 中明示且納入 RTP 計算，多數市場接受；但仍需逐市場確認 |
| 純表現層的個人化（美術、音效、任務提示） | 不影響期望值 |
| 依市場組態載入不同的固定數學配置 | 每個組態各自驗證與送測 |

### 2.3 灰區：需逐案確認的設計

| 機制 | 問題 | 處理 |
|------|------|------|
| 跨桌獎池必中上限 | 使獎池觸發依累積投入 | 多數市場接受累積型獎池的機制性質，但必須揭露並計入 RTP；向實驗室書面確認 |
| 任務／成就系統的固定獎勵 | 獎勵依累積行為達成 | 若獎勵是確定性的且其 RTP 貢獻已計入，通常可接受；若獎勵本身是隨機抽獎且機率隨進度變動，則屬違規 |
| 魚群密度依在座人數調整 | 影響命中機率 | 若調整規則是固定函式且不依營收或個人歷史，通常可接受，但必須在 PAR sheet 揭露並在各人數情境下驗證 RTP |
| 新手教學階段的固定高 RTP | 依玩家帳齡調整 | 若是免費試玩且與真錢遊戲明確分離，通常可接受。**部分市場要求免費試玩的機率必須與真錢相同**，若適用則不可行 |

灰區項目的處理原則：**揭露、量化、書面確認**。不揭露的灰區設計在送測時被發現，其後果與明確違規相同，因為它同時構成隱匿。

## 3. 如何在既有專案中找出控分

移植既有機台到線上時，控分邏輯通常已深植於程式碼，且原始開發者可能已不在。以下是有效的偵測方法。

### 3.1 靜態檢查

搜尋以下模式的變數與函式名稱：

```
accumul / cumulative / total_in / total_out / 累積 / 總投入 / 總產出
hold / holdRate / 抽水 / 回收率 / recovery
compensat / 補償 / adjust / correction
targetRtp / currentRtp / rtpDelta / rtpBias
difficulty / dda / dynamicDifficulty
memory / 記憶 / 記血 / carryOver
guarantee / 保底 / pity / failStreak
```

命中不代表違規，但每一處都必須追蹤到它是否進入捕獲判定的資料流。

### 3.2 判定函式簽章檢查

檢查捕獲判定函式的參數。若其簽章中包含以下任一項，即為控分嫌疑：

- 玩家累積統計物件
- 機台或桌次的累積投入／賠付
- 當前 RTP 或 RTP 偏差
- 玩家連續失敗次數
- 玩家餘額或儲值歷史
- 當前時間（除了作為隨機種子來源之外的用途）

理想的簽章只有：魚的狀態、砲倍、隨機位元組、已驗證的配置。見 `rng-capture-determination.md` 第 5.3 節。

### 3.3 行為測試（最可靠）

靜態檢查會漏，行為測試不會。

**測試 A：長期漂移測試**

以固定策略連續模擬數千萬發子彈，將 RTP 以滑動窗口（例如每 10 萬發）繪圖。

| 觀察 | 結論 |
|------|------|
| 曲線在目標值附近隨機波動，振幅隨窗口增大而縮小 | 無控分跡象 |
| 曲線呈現向目標值收斂的均值回歸，且低於目標後系統性回升 | **存在控分** |
| 曲線在低於目標時的上升速度明顯快於統計預期 | **存在控分** |

**測試 B：注入偏差測試**

人工強制連續 N 次失敗（直接操作模擬中的隨機來源），然後恢復正常隨機，觀察後續捕獲率。

| 觀察 | 結論 |
|------|------|
| 後續捕獲率與長期平均一致 | 無控分 |
| 後續捕獲率顯著高於長期平均 | **存在控分** |

**測試 C：狀態隔離測試**

在兩個完全獨立的伺服器實例上，以相同隨機序列執行相同操作序列，但其中一個實例事先執行了大量虧損操作。

| 觀察 | 結論 |
|------|------|
| 兩實例的結果序列完全相同 | 無跨局狀態依賴 |
| 結果序列不同 | **存在跨局狀態依賴** |

測試 C 是最強的證據，也是送測時可以主動提供給實驗室的自我驗證材料。

## 4. 移除控分後的後果

移除控分不是刪掉一段程式碼就結束。它會改變整個經濟模型。

### 4.1 數學模型必須重新驗證

控分存在時，實際 RTP 由控制器決定，賠率表與生命值配置的實際效果被控制器掩蓋。移除後，真實 RTP 才會顯現，且通常與名目設定不同。必須重新走完 `math-verification.md` 的完整流程。

### 4.2 波動性會顯著上升

控分的作用就是壓抑短期變異。移除後，場所業者會看到日回收率的波動大幅增加。這是預期行為，不是故障。這件事必須在專案早期就與商業方溝通，否則移除控分的技術決定會在上線後被商業壓力反轉。

### 4.3 商業模型可能需要調整

若場所業者的商業模型依賴可預測的日回收，正確的替代方案是：

| 需求 | 合規的解法 |
|------|-----------|
| 降低日回收波動 | 降低最高魚種倍數與變異，設計為低波動配置 |
| 限制單日最大損失 | 限制最高砲倍與單次最高賠付（並在 PAR sheet 明示） |
| 提高短期可預測性 | 提高體感命中率，降低稀有事件比重 |
| 保護新場所的現金流 | 這是商業與財務問題，不能用機率控制解決 |

**用數學模型設計降低波動是合規的；用控制器壓抑波動不是。** 兩者達成的商業目的相似，但一個是揭露的固定配置，一個是隱藏的動態調整。

## 5. 動態難度調整（DDA）的合規邊界

AI 個人化與動態難度是當前趨勢，也是最容易無意間造成違規的來源。

### 5.1 判準

唯一的判準是：**該調整是否改變任何玩家的期望值**。

| 調整對象 | 是否改變期望值 | 合規 |
|----------|----------------|------|
| 美術主題、配色、魚體外觀 | 否 | ✅ |
| 音效與音樂 | 否 | ✅ |
| UI 佈局與提示文案 | 否 | ✅ |
| 任務提示與引導 | 否（若任務獎勵本身不變） | ✅ |
| 推薦砲倍（僅建議，玩家可自由選擇） | 否 | ✅ 但需注意負責任遊戲層面 |
| 魚群密度 | 是（影響命中率） | ❌ 除非為固定函式且已揭露驗證 |
| 高倍魚出現頻率 | 是 | ❌ |
| 捕獲機率或傷害分佈 | 是 | ❌ |
| 特殊武器取得速度 | 是 | ❌ |
| BOSS 出現頻率 | 是 | ❌ |

### 5.2 架構建議

把表現層與判定層之間畫一道明確的架構邊界，並讓個人化系統**在編譯期就無法存取判定層的參數**。做法：

- 個人化服務不得寫入遊戲配置。
- 判定層的配置來源只有一個：已驗證雜湊的靜態配置檔。
- 個人化服務的輸出型別不包含任何數學參數。

這樣的架構本身就是送測時的說明材料，比「我們保證不會」有力得多。

## 6. 送測揭露義務

### 6.1 必須主動揭露的項目

即使您認為某項設計不構成控分，若它涉及任何跨局狀態，就必須主動揭露：

1. 所有跨局或跨座位持續存在的狀態變數，及其用途。
2. 跨桌獎池的抽取、累積、觸發與封頂機制。
3. 任務與成就系統的獎勵條件與 RTP 貢獻。
4. 魚群密度是否依在座人數變動，以及該函式的定義。
5. 免費試玩與真錢遊戲的機率是否相同。
6. 任何個人化系統的輸入與輸出，以及它與判定層的隔離方式。

### 6.2 不揭露的後果

隱匿的補償機制在送測中被發現，後果通常不只是退件：

| 情境 | 後果 |
|------|------|
| 送測階段被發現 | 退件，且該供應商後續提交通常進入加強審查 |
| 已認證但上線後被發現 | 認證撤銷，營運商可能面臨監管處分 |
| 台灣：經評鑑分類後修改軟體 | 依電子遊戲場業管理條例第 7 條，機具結構或軟體經修改者視為新型機種，須重新申請檢驗及評鑑分類 |
| 涉及賭博設計 | 台灣條例第 4 條明定電子遊戲機不得有賭博之設計及裝置；第 17 條第 1 項第 6 款禁止涉及賭博行為 |

台灣法源：https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=J0080024

## 7. 顧問對話流程

當開發者詢問「我們的機率控制程式能不能送測」：

1. **先確認他說的是什麼。** 「機率控制」可能指配置化的固定機率表（合規），也可能指補償控制器（違規）。請對方描述資料流：什麼輸入影響了捕獲判定。
2. **檢查判定函式簽章。** 這比任何描述都快。
3. **若確認為補償控制器，直接說明這是架構違規，不是參數問題。** 不要提供「調整參數讓它看起來不明顯」的建議。
4. **說明移除後的三個後果。** 數學需重驗、波動會上升、商業模型可能要調整。
5. **提供合規的替代方案。** 低波動配置設計、砲倍與賠付上限，能達成相近的商業目的。
6. **若對方的目標市場是娛樂機具而非博彩機具**，仍需確認該市場是否有派彩率或機制揭露要求。「不是博彩」不自動等於「沒有規範」。

## 8. 需要主動說出的事

1. **補償式控分是架構違規，不是參數違規。** 無法透過調整數值解決。
2. **保底機制也是控分。** 這一項最常被誤認為無害。
3. **「記血」是控分的變體。** 未擊殺的魚把傷害轉記到下一條，等同跨局狀態依賴。
4. **移除控分會讓波動大幅上升，這件事要在專案初期告知商業方。**
5. **降低波動的合規方法是設計低波動數學模型，不是加控制器。**
6. **AI 個人化只能作用在不影響期望值的表現層。**
7. **任何跨局狀態都必須主動揭露，即使您認為它合規。** 隱匿本身就是問題。
8. **台灣的認證後軟體修改視為新型機種**，需重新申請檢驗與評鑑分類，這使「上線後偷偷調參」在台灣同時是行政違規。
