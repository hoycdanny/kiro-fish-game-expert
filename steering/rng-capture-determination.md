# RNG 與捕獲判定實作工作流程指引

本指引涵蓋 CSPRNG 選擇、種子管理、每發子彈的獨立性、捕獲判定生命週期、魚群生成與路徑排程、伺服器權威命中判定、規則引擎，以及稽核日誌設計。

魚機的 RNG 使用點比老虎機多得多。老虎機一次旋轉呼叫 RNG 一次；魚機在同一秒內可能需要為 8 個座位的數十發子彈各自判定捕獲，同時為魚群生成決定物種、入場位置、速度與泳徑。每一個使用點都是潛在的合規缺口。

---

## 1. CSPRNG 選擇

### 1.1 硬性要求

所有影響玩家結果的隨機數必須來自密碼學安全來源。以下**不可用於任何結果性判定**：

| 語言／引擎 | 禁用 | 原因 |
|-----------|------|------|
| JavaScript/TypeScript | `Math.random()` | 非密碼學安全，可預測 |
| C# | `System.Random` | 非密碼學安全；同一 tick 建立的多個實例可能同種子 |
| C++ | `rand()`、`std::mt19937`（未加密種子） | 非密碼學安全 |
| Unreal | `FMath::RandRange`、`FMath::FRand` | 非密碼學安全 |
| GDScript | `randi()`、`randf()` | 非密碼學安全 |
| Python | `random` 模組 | 非密碼學安全（`secrets` 才是） |

### 1.2 各平台正確做法

| 執行環境 | CSPRNG |
|----------|--------|
| Node.js 伺服器 | `crypto.randomBytes()` / `crypto.randomInt()` |
| Go 伺服器 | `crypto/rand` |
| .NET 伺服器 / Unity | `System.Security.Cryptography.RandomNumberGenerator` |
| Unreal（伺服器） | OpenSSL `RAND_bytes()` |
| Godot | `Crypto.generate_random_bytes()` |
| Python（離線模擬） | `secrets` / `os.urandom()` |
| 瀏覽器 | `window.crypto.getRandomValues()`（僅非結果性用途） |

### 1.3 標準依據

- CSPRNG 設計依 NIST SP 800-90A Rev.1（DRBG 機制）、SP 800-90B（熵源）與 SP 800-90C（RBG 建構，2025-09 發布最終版）。
  - https://csrc.nist.gov/pubs/sp/800/90/a/r1/final
  - https://csrc.nist.gov/pubs/sp/800/90/c/final
- ⚠️ **NIST 自身立場是 SP 800-22 不應用於評估密碼學隨機數產生器。** 博彩業仍普遍引用該套件作為 RNG 合規基礎，此立場與現行 NIST 指引不一致。若客戶的送測文件以 SP 800-22 為主要依據，應主動指出並改以 800-90 系列為設計依據。
  - https://csrc.nist.gov/News/2022/decision-to-revise-nist-sp-800-22-rev-1a
- GLI 的 RNG 提交測試技術規格：https://gaminglabs.com/getting-started/technical-specifications-for-rng-testing/

### 1.4 效能考量與正確的解法

魚機的 RNG 呼叫頻率遠高於老虎機。滿座 8 人、每人每秒 5 發子彈，加上魚群生成，尖峰可達每秒數百次隨機數需求，跨桌則是這個數字乘以桌數。

**錯誤解法：** 因為效能而改用 `Math.random()` 或非密碼學 PRNG。這是直接的紅旗。

**正確解法：** 批次取樣。一次向 CSPRNG 請求大塊隨機位元組（例如 4 KB），存入緩衝區，判定時從緩衝區取用，用盡後重新填充。緩衝區內容仍然完全來自 CSPRNG，只是攤平了系統呼叫成本。實作要點：

- 緩衝區必須是每個工作處理程序私有，不可跨處理程序共用同一緩衝區位置指標。
- 緩衝區與其位置指標不得被序列化、快照或寫入日誌明文。
- 重新填充失敗時必須讓判定失敗並記錄事故，**不得回退到非密碼學來源**。
- 在送測文件中明確說明批次取樣機制與緩衝區生命週期，否則實驗室可能誤判為自製 PRNG。

## 2. 每發子彈的獨立性

### 2.1 要求

每發子彈的捕獲判定必須與以下無關：

- 該玩家先前的捕獲或失敗紀錄
- 該座位或該桌的累積投入與累積賠付
- 機台或伺服器的當前 RTP 偏差
- 該玩家的帳戶餘額或儲值歷史
- 時段、上線人數或營收目標

唯一允許影響判定的狀態是**該條魚當前的剩餘生命值**，因為那是遊戲規則的一部分且對玩家可見（或至少可推論）。

### 2.2 剩餘生命值不違反獨立性，但必須正確界定

「這條魚已被打掉 80% 生命值，所以下一發更可能捕獲」不是違規——它是規則。但以下界線必須守住：

| 允許 | 禁止 |
|------|------|
| 依該魚剩餘生命值決定是否捕獲 | 依該玩家歷史調整每發傷害的期望值 |
| 魚的初始生命值由該魚種的固定分佈決定 | 魚的初始生命值依當前 RTP 偏差調整 |
| 每發傷害從固定分佈抽樣 | 傷害分佈的參數隨累積投入變動 |
| 魚離場清除其生命值狀態 | 魚離場時把已投入傷害「記帳」到下一條魚 |

最後一項在魚機產業很常見（「打不死的魚會把血記在下一隻」），它是補償機制的變體，見 `payout-control-integrity.md`。

### 2.3 生命值狀態的歸屬

生命值是**魚的屬性，不是玩家的屬性**。多名玩家射擊同一條魚時，共同扣減同一份生命值。這是設計選擇，也是傷害歸屬問題的來源，見 `multiplayer-fairness.md`。

若改為「每個玩家對每條魚有獨立的血量進度」，則同桌其實是視覺共享而非機制共享。這是合法設計，但必須在 PAR sheet 與玩家規則中明示，否則構成誤導呈現。

## 3. 捕獲判定生命週期

每發子彈必須走完以下六階段，且**全部在伺服器端**。

```
階段 1  發射請求（Fire Request）
        ├─ 驗證座位有效、玩家已認證、帳戶狀態允許下注
        ├─ 驗證砲倍在允許範圍
        ├─ 驗證射速未超過上限（防連發外掛與市場循環時間要求）
        └─ 產生 bulletId（伺服器產生，不接受客戶端提供）

階段 2  扣款（Debit）
        ├─ 以 bulletId 作為幂等鍵向錢包扣除砲倍金額
        ├─ 餘額不足則拒絕並回傳明確原因
        └─ 扣款成功後才允許進入判定

階段 3  彈道與命中判定（Trajectory & Hit Resolution）
        ├─ 以伺服器權威的魚群狀態計算子彈路徑
        ├─ 以伺服器 tick 時間軸推進，不採用客戶端時間戳
        ├─ 決定是否命中，命中哪一條魚（fishId）
        └─ 未命中則進入階段 6

階段 4  捕獲判定（Capture Resolution）
        ├─ 自 CSPRNG 取樣決定本發傷害
        ├─ 扣減該 fishId 的剩餘生命值
        ├─ 生命值 ≤ 0 則捕獲成立
        └─ 記錄 RNG 原始輸出值

階段 5  賠付（Credit）
        ├─ 賠付 = 魚種賠率倍數 × 砲倍
        ├─ 以 captureId 作為幂等鍵向錢包入款
        ├─ 多人共同擊殺時依分配規則結算（multiplayer-fairness.md）
        └─ 更新跨桌獎池抽取

階段 6  稽核記錄與廣播（Audit & Broadcast）
        ├─ 寫入稽核日誌（第 6 節欄位）
        ├─ 寫入對局重播事件流
        └─ 向該桌所有座位廣播權威結果
```

### 3.1 客戶端的角色

客戶端可以做視覺預測（預先播放子彈飛行與命中特效），但：

- 客戶端**不得**決定是否命中。
- 客戶端**不得**決定是否捕獲。
- 客戶端**不得**決定賠付金額。
- 客戶端的預測結果與伺服器權威結果不符時，必須以伺服器結果覆蓋，並且覆蓋必須在體感上可接受（見 `multiplayer-fairness.md` 的回滾處理）。

**「客戶端判定、伺服器驗證」不等於伺服器權威。** 若伺服器只是檢查客戶端上報的結果是否「合理」，攻擊者仍可在合理範圍內選擇對自己最有利的結果。判定必須由伺服器產生。

### 3.2 射速上限

射速直接決定投注速度。實作上必須在伺服器端強制上限，理由有三：

1. 防止連發外掛造成的異常投注速度。
2. 部分市場對遊戲循環時間有硬性下限，若適用，射速即為受規範參數。
3. 射速失控會讓玩家在極短時間內損失大量金額，構成負責任遊戲風險（`responsible-gaming.md`）。

自動發射（auto-fire）功能在部分市場受限或禁止，處理方式見 `responsible-gaming.md`。

## 4. 魚群生成與路徑排程

### 4.1 生成也是結果性隨機

魚群生成決定了「畫面上有什麼魚可以打」，直接影響 RTP。因此生成用的隨機數與捕獲判定同等級：**必須用 CSPRNG，必須在伺服器端，必須記錄**。

常見錯誤：捕獲判定嚴謹地用了 CSPRNG，但魚群生成在客戶端用 `Math.random()` 產生，導致每個客戶端看到不同的魚群，或使魚群可被預測。

### 4.2 生成參數

| 參數 | 隨機或排程 | 備註 |
|------|-----------|------|
| 物種 | 依配置權重隨機 | 權重即 `math-model.md` 的池中數量目標 |
| 入場位置與方向 | 隨機 | 應避免長期偏向特定座位（見公平性） |
| 移動速度 | 依物種的固定分佈隨機 | 影響命中難度，屬數學模型參數 |
| 泳徑 | 從預定義路徑集合隨機選取，或程序化生成 | 若程序化，種子必須記錄 |
| 初始生命值 | 依物種的固定分佈隨機 | **不得依 RTP 偏差調整** |
| 群體出現（魚群陣列） | 排程事件 | 排程本身可以是確定性的，但需揭露 |

### 4.3 場景與 BOSS 排程

場景輪替與 BOSS 出現可以是**確定性排程**（例如每 3 分鐘輪替一次場景），這比隨機更容易稽核，也不影響獨立性——只要排程不依玩家行為或營收狀態。

若 BOSS 出現是隨機的，其觸發機率必須是固定常數，並在 PAR sheet 揭露。

### 4.4 確定性重播的必要條件

為了支援對局重播（`platform-systems-compliance.md`），魚群生成必須可以確定性重現。做法：

1. 每個桌次的每個時間窗使用一個記錄下來的**生成種子**。
2. 生成邏輯為純函式：`(seed, tick) → 生成事件`。
3. 種子由 CSPRNG 產生（因此不可預測），但一旦產生就記錄下來（因此可重播）。
4. 種子在該時間窗結束前不得洩漏給客戶端。

這個模式同時滿足「不可預測」與「可稽核重播」，是魚機系統設計的關鍵手法。**若採用此模式，必須在送測文件中說明：種子由 CSPRNG 產生，記錄用於重播，不用於預先決定結果。** 否則容易被誤判為預先決定結果（pre-determined outcome）。

## 5. 規則引擎設計

### 5.1 配置外部化

以下必須是外部化的宣告式配置，不是散落在程式碼中的常數：

- 魚種賠率表（賠率倍數、生命值分佈、生成權重）
- 傷害分佈參數
- 砲倍檔位
- 特殊武器的取得條件、效果與持續時間
- 場景輪替與 BOSS 排程
- 跨桌獎池抽取比例與層級

理由有三：認證機構需要逐項審查這些數值；市場差異需要不同組態；變更管理需要能比對版本差異（`change-management-recert.md`）。

### 5.2 配置完整性驗證

伺服器啟動時必須驗證：

| 檢查 | 失敗處理 |
|------|----------|
| 配置檔雜湊值符合已認證的雜湊 | 拒絕啟動並告警 |
| 生成權重總和為正且各項非負 | 拒絕啟動 |
| 每個魚種都有賠率倍數與生命值分佈 | 拒絕啟動 |
| 各砲倍的理論 RTP 一致（離線預計算值） | 拒絕啟動 |
| 跨桌獎池抽取比例在允許範圍 | 拒絕啟動 |

**拒絕啟動優於降級運行。** 用錯誤數學組態營運的每一秒都在產生需要事後補償的交易。

### 5.3 純函式判定

捕獲判定應實作為純函式：

```
resolveCapture(
  fishState: FishState,        // 物種、剩餘生命值
  betMultiplier: number,       // 砲倍
  rngBytes: Uint8Array,        // 本次判定使用的隨機位元組
  config: GameConfig           // 已驗證的配置
): CaptureResult
```

沒有隱藏狀態、沒有全域計數器、沒有玩家歷史參數。**函式簽章本身就是獨立性的證明**，這在送測審查中比任何文字說明有力。若您的判定函式需要傳入玩家歷史或累積統計，那個參數就是需要解釋的合規問題。

## 6. 稽核日誌設計

### 6.1 每發子彈的必要欄位

| 欄位 | 說明 |
|------|------|
| `bulletId` | 伺服器產生的唯一識別碼，亦為扣款幂等鍵 |
| `timestamp` | ISO 8601，伺服器時間，含毫秒 |
| `serverTick` | 伺服器 tick 序號，用於重播對齊 |
| `tableId` | 桌次識別碼 |
| `seatId` | 座位識別碼 |
| `sessionId` | 工作階段識別碼 |
| `playerId` | 玩家識別碼 |
| `betMultiplier` | 砲倍 |
| `betAmount` | 實際扣款金額 |
| `aimAngle` | 客戶端提交的瞄準角度（輸入，不是結果） |
| `hitResult` | 是否命中，命中的 `fishId` 與物種 |
| `rngOutput` | 本次判定取用的原始隨機值 |
| `damageDealt` | 本發造成的傷害 |
| `fishHpBefore` | 命中前該魚剩餘生命值 |
| `fishHpAfter` | 命中後該魚剩餘生命值 |
| `captured` | 是否捕獲 |
| `payoutMultiplier` | 魚種賠率倍數（若捕獲） |
| `payoutAmount` | 賠付金額（若捕獲） |
| `damageAttribution` | 多人共同擊殺時的傷害歸屬明細 |
| `balanceBefore` | 扣款前餘額 |
| `balanceAfter` | 結算後餘額 |
| `configHash` | 當時生效的配置雜湊 |
| `buildHash` | 當時運行的建置雜湊 |

### 6.2 魚生命週期日誌

除了每發子彈，還必須記錄魚的生命週期，否則無法解釋「為什麼我打了 20 發的魚不見了」：

| 事件 | 必要欄位 |
|------|----------|
| 魚生成 | `fishId`、物種、初始生命值、入場位置、速度、泳徑識別、`spawnSeed`、`serverTick` |
| 魚被擊殺 | `fishId`、擊殺 `bulletId`、傷害歸屬明細、賠付分配 |
| 魚離場 | `fishId`、離場原因（游出畫面／場景重置／關卡結束）、剩餘生命值、已累積投入的傷害來源 |

**魚離場事件是魚機稽核的必要項，也是最常被省略的。** 玩家爭議中「我明明快打死了」的答案就在這裡。同時它也是 `math-verification.md` 第 15 節損失項的資料來源。

### 6.3 日誌完整性

- 稽核日誌必須是**唯附加（append-only）**，不可就地更新。
- 應具備防篡改機制（雜湊鏈或簽章），使事後修改可被偵測。
- 保存期依市場要求，見 `jurisdiction-matrix.md` 與 `data-protection-privacy.md`。
- 日誌寫入失敗必須視為事故，不可靜默丟棄。

### 6.4 資料量估算

滿座 8 人、每人每秒 5 發、每桌每秒 40 筆子彈日誌。以每筆 400 位元組估算，單桌每小時約 55 MB。100 桌全天運轉約 130 GB／日。乘上市場要求的保存期就是實際的儲存成本，必須在架構階段估算而非事後發現。

壓縮與分層儲存（熱資料保留完整欄位、冷資料保留可重播的最小事件流）是標準做法，但**壓縮不得損失重播所需的欄位**。

## 7. 需要主動說出的事

1. **`Math.random()` 或任何非密碼學來源用於捕獲判定或魚群生成，是最高優先級紅旗。** 應中斷當前討論優先處理。
2. **魚群生成常被遺漏。** 捕獲判定用 CSPRNG 但生成用弱隨機，是實務上最常見的漏洞。
3. **「客戶端判定、伺服器驗證」不是伺服器權威。** 這個誤解會在系統層審查時被直接指出。
4. **效能問題用批次取樣解決，不是換 PRNG。**
5. **魚離場日誌是必要項。** 沒有它，玩家爭議無法處理，損失項也無法驗證。
6. **判定函式的簽章就是獨立性的證明。** 若簽章中有玩家歷史參數，就有需要解釋的合規問題。
7. **配置雜湊不符應拒絕啟動。** 降級運行會產生需要事後補償的交易。
